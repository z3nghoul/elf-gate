# Дополнения к плану (поверх SPEC.md)

SPEC.md не правится. Уточнения, принятые в ходе работы, записываются здесь и учитываются
при реализации соответствующего этапа.

## Этап 6. Подписки, пинг: проверка конфигов Xray

Сейчас `xray::validate::check` запускает `xray run -test` для каждого сервера при добавлении,
при старте приложения и перед подключением. Для подписок на сотни серверов это надо
оптимизировать:

- **Кеш вердиктов** `xray run -test` по ключу: хеш сгенерированного конфига + версия Xray
  (вывод `xray version`). Один и тот же конфиг на той же версии повторно не проверяется.
  Кеш хранится в `state.json` (или отдельным файлом рядом) и сбрасывается при смене версии Xray.
- **Фоновая проверка** с лимитом 4 параллельных процессов `xray run -test`
  (так же, как URL-пинг), интерфейс не блокируется.
- **Перепроверка только изменившихся серверов**: при обновлении подписки проверяются
  серверы, у которых изменился хеш конфига; остальные берут вердикт из кеша.
- Проверка перед подключением остаётся, но использует кеш (без запуска процесса, если ключ найден).

## Этап 3 (сделано)

## Этап 4 (сделано)

- Прежние настройки прокси сохраняются в `state.json` до изменения и восстанавливаются из него
  при выходе, panic hook, SIGTERM/SIGHUP/консольных событиях и при следующем запуске после сбоя.
- Команды системного прокси выполняет один выделенный поток (порядок команд, UI не блокируется).
- Трейт: `current()` возвращает снимок настроек, `disable(previous)` восстанавливает его,
  `enable(addr, bypass)` принимает `ProxyAddr` (HTTP и SOCKS порты), а не одну строку.
- Известное ограничение: нет защиты от двух одновременно запущенных экземпляров.

## Этап 6. Автоматический перебор TLS fingerprint

Находка с живого сервера: у части российских провайдеров соединение с `fp=chrome` ломается
(в логе сервера Xray `REALITY: processed invalid connection ... failed to read client hello`;
вероятно, большой ClientHello с постквантовым ключом режется ТСПУ), а с `fp=firefox` тот же сервер работает.

Сейчас fp меняется вручную (клавиша `f`, переопределение в `[[overrides]]` в `config.toml`, подсказка
«попробуйте fp=firefox», когда ядро логирует серию ошибок). На этапе 6, вместе с пингом:

- Если сервер недоступен с текущим fp (URL-пинг не проходит, а TCP-пинг проходит), автоматически
  перебрать fp в порядке `firefox`, `chrome`, `safari`, `ios`, `edge`, `random`, `qq` и проверить каждый
  временным ядром (как URL-пинг, не более 4 параллельно).
- Первый сработавший fp предложить пользователю (или применить как переопределение с пометкой
  «подобран автоматически»); результат кешировать по серверу, перепроверять при смене версии Xray.
- Параметр `fp` из ссылки не подменять: подобранное значение живёт только в переопределении.

## Уточнения пользователя (ноябрь 2026)

Целевая схема: максимум два сервера. Прямой (Финляндия) и запасной каскадный вход в РФ для режима
белых списков. Большие пулы серверов не приоритет.

### Этап 6. Автопереключение основной / запасной сервер

- Автопереключение делается под схему «основной + запасной», а не под большие пулы.
- Проверка доступности средствами Xray (`observatory` / `burstObservatory`), а не своим пингом.
- Возврат на основной сервер, когда он снова доступен (с гистерезисом, чтобы не дёргать соединение).
- Пользователь явно назначает роли (основной, запасной) в настройках сервера.
- Это относится к 4-му пункту плана этапа 6 про перебор fp: перебор остаётся, но не на сотнях серверов.

### Этапы 2 и 7. Фрагментация TLS ClientHello

- Опция на сервер, настраивается через настройки Xray (`fragment` в `sockopt.dialerProxy` или
  `freedom` с `fragment`, способ выбрать при реализации и проверить `xray run -test`).
- По умолчанию выключена. Переключается в деталях сервера рядом с fp, сохраняется как
  переопределение в `[[overrides]]` в `config.toml` (как fp).
- В `Server` появляется поле переопределения, генератор конфига добавляет настройку только при включении.

### Этап 7. Пресет «блокировать UDP 443 (QUIC)»

- Правило `network = udp`, `port = 443` с `outboundTag = block`, чтобы браузеры уходили с QUIC на TCP.
- Оформляется как встроенный пресет в `presets.toml`, **по умолчанию включён**.
- Важно для Discord: голос и стримы Discord идут по UDP на других портах, блокировка касается
  только 443. Проверить это в исследовании 5.1 и на живом сервере.

## Этап 5 (из исследования 5.1, см. docs/tun-research.md)

- Эвристика подсказки про `fp` опирается на предупреждения и ошибки ядра, но ошибки рукопожатия Xray пишет на уровне

## Этап 5.2 (сделано, см. docs/tun-research.md раздел 10 и docs/linux-tun-setup.md)

- TUN самого Xray; Linux: копия Xray `root:root` с `cap_net_admin` (команды показываются в UI), запасной путь `sudo elf-gate`;
  Windows: перезапуск с правами администратора через `--tun`.
- Домен VPS резолвится до подъёма TUN при каждом подключении; домены правил «через VPN» резолвятся через туннель.
- Проверка соединения (`generate_204` через socks) вместо подсказки по логам; тот же механизм для автопереключения (этап 6).
- `rp_filter`: предупреждение с командой, настройки не меняются. Экран правил с выбором процесса из запущенных.
- Первый запуск TUN предлагает `discord-only`; режим по умолчанию `exclude`.
- Не сделано сейчас (этап 7): пресет `block-quic` включён по умолчанию (пока выключен; при flow=vision UDP/443 уже закрыт самим Xray),
  редактирование регистра имён процессов Windows, проверка имён Linux-пресетов на установленных клиентах.

## Пожелания пользователя (ноябрь 2026, после этапа 5.2)

### Этап 6. `auto_connect` и автозапуск при входе в систему

- Настройка `auto_connect` (по умолчанию **выключена**): при старте подключаться к последнему серверу
  (`[ui].last_server`) в последнем режиме трафика (`[mode].traffic`, PROXY или TUN). Основа уже есть: флаг `--tun`
  и `start_tun_from_cli` из этапа 5.2.
- Опция «запускать при входе в систему», включается из экрана настроек (этап 8):
  - Windows: значение в `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` или ярлык в папке автозагрузки;
  - Linux: файл `.desktop` в `~/.config/autostart`.
- Автозапуск запускает **фоновый процесс** (этап 7.5), а не TUI. Пока 7.5 нет, консольное окно без TUI не скрыть, поэтому
  до 7.5 автозапуск при входе либо не включается в релиз, либо помечается в настройках как временное решение.

### Этап 7.5 (новый). Фоновый режим и трей

Цель: VPN живёт независимо от окна TUI; управление из трея и из TUI.

**Архитектура**
- `elf-gate --background`: фоновый процесс без окна. **Владеет** ядром Xray, системным прокси, TUN, состоянием
  (`state.json`), очисткой при сбоях и иконкой в трее. Права для TUN (Windows: администратор, Linux: capability-копия
  ядра) нужны только ему, что заодно убирает танец «перезапуск с UAC» из TUI: TUI работает без повышения.
- TUI это клиент: подключается к фоновому процессу по **локальному IPC**:
  - Windows: именованный канал `\\.\pipe\elf-gate-<пользователь>` с DACL только для текущего пользователя;
  - Linux: unix-сокет `$XDG_RUNTIME_DIR/elf-gate.sock` (права `0600`, каталог `0700`).
- **Закрытие TUI не рвёт VPN.** Если фонового процесса нет, TUI предлагает его запустить (или запускает сам).
- **Один фоновый процесс на пользователя**: сокет или канал служат ещё и замком одного экземпляра. Это закрывает известное
  ограничение «нет защиты от двух одновременных экземпляров» (этап 4, `docs/plan-additions.md`).
- Протокол IPC: команды (`connect`, `disconnect`, `set_mode`, `select_server`, правила, настройки) и поток событий
  (состояние, логи, результат проверки соединения). Через IPC не передаются ссылки на серверы и секреты целиком: клиент
  видит имена, а полные ссылки остаются в `config.toml`.
- Ответственность за аварийную очистку (panic hook, SIGTERM/SIGHUP, консольные события, сторож ядра на Linux, `state.json`)
  переезжает в фоновый процесс; TUI может падать без последствий для системного прокси и туннеля.

**Трей**
- Меню: подключиться, отключиться, выбор сервера, переключить PROXY/TUN, открыть интерфейс, выход. Иконка показывает
  состояние: подключено / не подключено / ошибка (и, возможно, «идёт подключение»).
- В Windows Terminal окно консоли скрыть нельзя, поэтому трей живёт **в фоновом процессе, а не в TUI**.
  Фоновый процесс на Windows собирается без консоли: отдельный `elf-gate-bg.exe` с `windows_subsystem = "windows"` либо
  тот же `elf-gate.exe`, который при `--background` отсоединяется от консоли (`FreeConsole`); выбор делается при реализации
  с проверкой, что вывод TUI-варианта не ломается. «Открыть интерфейс» запускает `wt elf-gate.exe` (или консоль по умолчанию).

**Крейты (предложение, с обоснованием)**
- `tray-icon` + `muda` (проект tauri-apps): активно поддерживаются, кроссплатформенные, одно меню на Windows (Win32) и Linux.
  Минус на Linux: требуют GTK и `libayatana-appindicator`/`libappindicator3` и цикл событий GTK в потоке фонового процесса.
- Альтернатива для Linux: `ksni` (StatusNotifierItem по D-Bus на чистом Rust, без GTK), а `tray-icon` оставить только на Windows.
  Это легче по зависимостям и лучше работает в KDE, но даёт два пути кода. Решение принимается на старте этапа 7.5 после проверки
  на KDE (нужна Wayland-сессия) и GNOME (там для трея нужно расширение AppIndicator).
- IPC: крейт `interprocess` (именованные каналы и unix-сокеты с поддержкой tokio) вместо ручных `windows`/`nix`-обёрток.
  Добавление зависимостей будет объяснено при реализации.

**Поведение без трея на Linux**: если нет StatusNotifier/appindicator (минимальные окружения, GNOME без расширения),
фоновый режим **работает как обычно, просто без иконки**: управление через TUI и IPC. Отсутствие трея не ошибка, а строка в журнале.

**Связь с этапом 6**: автозапуск при входе и `auto_connect` запускают фоновый процесс; он сам подключается к последнему серверу
в последнем режиме. TUI при запуске лишь присоединяется к нему.

**Проверки (план)**: сквозной тест в лаборатории (`docs/tun-research/lab`) с настоящим фоновым процессом: TUI закрыт, VPN работает;
второй фоновый процесс не стартует; `kill -9` TUI не затрагивает туннель; `kill -9` фонового процесса оставляет очистку следующему запуску;
IPC недоступен другим пользователям (права `0600` / DACL).
