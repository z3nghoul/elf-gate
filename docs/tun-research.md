## 2. Ответы на пункты SPEC 5.1

### 2.1 Есть ли TUN-инбаунд в Xray, как настраивается, какие файлы

- **Есть.** `protocol: "tun"`, пакет `proxy/tun` в бинарнике 26.11.9. Windows, Linux, macOS, FreeBSD. [РУКАМИ: бинарник; ДОК]
- Поля `settings` [ДОК, имена полей сверены с бинарником]:

| Поле | Смысл |
|---|---|
| `name` | имя интерфейса (по умолчанию `utunN`; на Windows существующий адаптер Wintun с таким именем переиспользуется) |
| `desc` | только Windows, описание адаптера (по умолчанию `Wintun`) |
| `mtu` | по умолчанию 1500 |
| `gateway` | адреса интерфейса, например `["10.0.0.1/16","fc00::1/64"]`. На Linux без него адрес не назначается |
| `dns` | DNS-серверы интерфейса, **только Windows** |
| `userLevel` | уровень политики |
| `autoSystemRoutingTable` | CIDR, которые Xray сам добавляет в таблицу маршрутов (`["0.0.0.0/0","::/0"]`), все ОС |
| `autoOutboundsInterface` | привязка исходящих Xray к физическому интерфейсу (`"auto"` или имя), защита от петли |
| `autoSystemDnsToGateway` | Linux и FreeBSD: направить системный DNS на TUN (Linux: `resolvectl`, нужен systemd-resolved 240+) |
| `autoSystemWfpBlockLeak` | **только Windows**: фильтры WFP, блокирующие утечки (`dns`, `misconfigtun`, `all`, ...) |

- **Что делает Xray на Linux** [РУКАМИ]: создаёт интерфейс, поднимает его, назначает `gateway`, добавляет маршрут
  `default dev xray0 metric 1`. `ip rule` не трогает. После `kill -9` интерфейс и маршруты исчезают сами
  (TUN-устройство не постоянное).
- **Файлы**: на Linux только `/dev/net/tun`. На Windows нужен `wintun.dll`. Он **есть в официальном архиве
  Xray-windows-64.zip** (`wintun.dll`, 427 552 байта, рядом `LICENSE-Wintun`). [РУКАМИ: содержимое архива] В документации
  Xray про `wintun.dll` не сказано. [ДОК]
- Версию, с которой TUN появился, документация не называет.

### 2.2 Правило маршрутизации по имени процесса

- **Есть**: поле `process` в правиле маршрутизации (`router.ProcessNameMatcher`). [РУКАМИ: бинарник; ДОК]
- Синтаксис [ДОК]: массив строк, три режима: без слеша это имя процесса, со слешем это абсолютный путь,
  со слешем на конце это папка. **Регистр важен.** Имя без `.exe`: ядро само отрезает `.exe`, поэтому
  `["curl"]` работает и на Linux, и на Windows. С путём `.exe` обязателен, слеши прямые (`C:/Windows/System32/curl.exe`).
  Спецзначения: `self/` (само ядро, «очень полезно против петель») и `xray/` (все процессы из этого бинарника).
- Поддержка ОС [ДОК]: **только Windows и Linux** (macOS не поддерживается). Совпадает только соединение,
  **исходящее с этой же машины**, иначе правило не срабатывает.
- **Проверено в режиме TUN** [РУКАМИ Linux, лаборатория, сценарий `02-process-routing`]:

| Режим | Правило | Результат |
|---|---|---|
| `include` (по умолчанию direct) | `curl`, `socat1` -> proxy | curl TCP и socat UDP **через VPN**, python TCP и UDP **напрямую** |
| `exclude` (по умолчанию proxy) | `python3.14` -> direct | python TCP и UDP **напрямую**, curl TCP и socat UDP через VPN |

- **Ловушка №1: имя это имя реального файла после разрешения симлинков.** `python3` на этой машине это
  `/usr/bin/python3.14`, а `socat` это `/usr/bin/socat1`: правила `python3` и `socat` **не срабатывали**,
  `python3.14` и `socat1` сработали. [РУКАМИ] Для пресетов это значит: имена надо проверять на реальных
  дистрибутивах (для Discord на Linux это `Discord` или `vesktop`, для Flatpak и Snap путь другой), а пользователю
  нужен способ увидеть «какое имя процесса видит ядро» (например, из лога ядра или списка запущенных).
- Как Xray определяет процесс по соединению, в документации не сказано. Из текстов бинарника видно, что используется
  поиск по адресу источника (`process lookup requires a source IP`), на Linux этого достаточно для TUN, так как
  исходные порты принадлежат сокетам приложений. [РУКАМИ: работает; механизм по строкам бинарника]
- На Windows работа этого механизма в TUN [НЕ ПРОВЕРЕНО]. Один отчёт пользователя v2rayN говорит, что правила по
  PID в режиме TUN у них не работали (это не Xray, а оболочка). [ДОК, косвенно]

### 2.3 Если чего-то нет: sing-box (вариант B)

### 2.4 UDP через VLESS (Xray, xudp): голос и демонстрация экрана Discord

Лаборатория: клиент в TUN, UDP-эхо на «интернете», сервер с VLESS (сценарии `01`, `04`). [РУКАМИ]

| Вариант | UDP на обычном порту | UDP/443 | TCP |
|---|---|---|---|
| VLESS tcp, `encryption=none` | 0 потерь (100, 1200, 1400 байт) | не проверялось | работает |
| Reality + `flow=xtls-rprx-vision` | **0 потерь**, p50 ~0,3-0,5 мс | **100% потерь (блокирует Vision)** | работает |
| Reality + `flow=xtls-rprx-vision-udp443` | 0 потерь | **проходит** | работает |
| Reality без flow (сервер требует Vision) | работает | работает | **не работает** |

- Документация Xray подтверждает: при XTLS UDP/443 блокируется по умолчанию (чтобы браузеры падали с QUIC на TLS),
  `xtls-rprx-vision-udp443` это отключает. [ДОК, РУКАМИ]
- **Каждый UDP-поток (каждый исходный порт) это отдельное TCP-соединение VLESS** (в журнале сервера по строке
  `accepted udp:...` на поток). [РУКАМИ] Для Discord это нормально: голос идёт одним сокетом.
  Если потоков много, соединений тоже много. «xudp» (`packetEncoding`) объединяет их, это не проверялось. [НЕ ПРОВЕРЕНО]
- Для голоса Discord на клиенте и сервере **ничего дополнительного настраивать не нужно** сверх обычного VLESS
  (UDP в серверном инбаунде включён по умолчанию, ограничений нет). Размеры датаграмм до 1400 байт прошли без потерь. [РУКАМИ]
- **Не проверено вообще**: настоящий Discord (голос, демонстрация экрана), задержки по реальному каналу, джиттер,
  поведение при потере пакетов. Лабораторные 0,3-0,5 мс это стоимость локального стека, а не сети. [НЕ ПРОВЕРЕНО]
- **Следствие для вашего пресета «блокировать UDP 443»**: при `flow=xtls-rprx-vision` QUIC уже блокируется самим Xray на
  клиенте. Отдельное правило нужно для серверов без Vision (TLS, ws, xhttp) и как явная настройка. Голос Discord
  (высокие UDP-порты) блокировка 443 не затрагивает. [РУКАМИ + из общих знаний о портах Discord, НЕ ПРОВЕРЕНО на Discord]
- Накладные расходы TUN [РУКАМИ, лаборатория, без реального канала]: 600 МБ через Reality + Vision в TUN прошли со скоростью
  порядка 230-920 МБ/с, процесс Xray занял около 1 с CPU и 52 МБ памяти. Узким местом не будет.

### 2.5 Требования окружения

**Права.**

- Linux [РУКАМИ + ДОК]: нужен `CAP_NET_ADMIN`. Без него Xray падает с сухим
  `Failed to start: app/proxyman/inbound: failed to start proxy > operation not permitted`. Это сообщение надо
  перехватывать и заменять понятным. В моей лаборатории права даёт user namespace, на реальной машине нужен
  root (`sudo elf-gate`) или `setcap cap_net_admin+ep` на бинарник (`setcap` без root проверить нельзя: [НЕ ПРОВЕРЕНО]).
- Windows [ДОК, НЕ ПРОВЕРЕНО]: права администратора (Wintun, маршруты, WFP). Документация Xray это явно не пишет.

**DNS.**

- Linux [ДОК]: `autoSystemDnsToGateway` переключает systemd-resolved через `resolvectl` на адрес TUN, нужен
  systemd-resolved 240+, **нужно, чтобы маршрутизация отправила порт 53 этого инбаунда на DNS-аутбаунд, иначе Xray не
  стартует**. При убийстве Xray (`SIGKILL`) настройку надо откатывать руками (`resolvectl revert <интерфейс>`).
  **Я это не запускал**: через D-Bus это изменило бы настоящий systemd-resolved вашей машины. [НЕ ПРОВЕРЕНО]
  На вашей машине (`wlan0`, KDE) resolved есть.
- Windows [ДОК]: `dns` в настройках TUN и `autoSystemWfpBlockLeak: ["dns", ...]`, иначе «многоадресный» DNS Windows
  утекает мимо туннеля.
- **Риск для режима «только Discord» (`include`)** [НЕ ПРОВЕРЕНО, логика]: приложение спрашивает системный DNS (прямо,
  у провайдера). Для заблокированных в РФ доменов он может вернуть чужой адрес, и Discord пойдёт на мёртвый IP через
  VPN. Лекарство в Xray: sniffing (`http`, `tls`) в TUN-инбаунде, чтобы сервер сам резолвил домен из SNI. Для UDP голоса
  Discord адреса приходят от API по IP, DNS там не участвует. Это нужно проверить на живом сервере.

**Защита от петли** [РУКАМИ, сценарий `03-loop-protection`].

| Вариант | Результат |
|---|---|
| VPS по IP, `autoOutboundsInterface: "auto"` (автоматически, если задан `autoSystemRoutingTable`) | **работает** |
| VPS по IP, маршруты вручную, без защиты | **не работает** (трафик Xray возвращается в туннель) |
| то же + статический маршрут до VPS через физический интерфейс | работает |
| **VPS по домену**, `auto`, системный резолвер | **не работает**, DNS-сервер запрос не получил |
| VPS по домену, `auto`, явный `dns.servers` | **не работает**, тот же результат |
| VPS по домену, имя есть в `/etc/hosts` | работает |

- Без TUN (socks-режим) тот же домен резолвится нормально (запрос приходит с физического адреса). То есть дыра именно
  в сочетании TUN + сетевой резолв домена VPS. Причину внутри Xray я не искал.
- **Вывод: адрес VPS-домена надо резолвить самим до включения TUN и подставлять в аутбаунд IP** (SNI и host остаются доменом).
  Тогда зависимости от DNS внутри туннеля нет вообще. Если у домена несколько адресов или он меняется, резолвить
  при каждом подключении.
- В варианте B защита от петли ручная: правило `process_name: ["xray"] -> direct` (или по IP VPS). Без него режим
  `exclude` ломается так же. [РУКАМИ]

**Сон, смена сети (Wi-Fi <-> кабель, выход из сна)** [НЕ ПРОВЕРЕНО]. Документация это не описывает. `autoOutboundsInterface`
следит за сменой интерфейса (в бинарнике есть `InterfaceUpdater`, в логе «update interface vA 3»), но поведение при сне
и смене маршрутов не проверялось. Нужны живые проверки на реальном железе.

**Очистка после аварии** [РУКАМИ Linux]: `kill -9` Xray: интерфейс и маршруты исчезли. Для DNS (если включать
`autoSystemDnsToGateway`) нужен откат вручную, и приложению придётся делать его при следующем старте.

## 3. Находки и ловушки (то, что сломало бы продукт молча)

1. **Имя процесса = реальный файл** (раздел 2.2). `python3` не совпал с `python3.14`.
2. **`rp_filter`.** Xray на Linux добавляет `default dev xray0 metric 1`, а «прямые» соединения привязаны к физическому
   интерфейсу. Ответ приходит на физический интерфейс, а лучший маршрут до его источника ведёт в туннель. При
   **строгом** `rp_filter=1` такой ответ отбрасывается, и всё, что идёт «direct» через TUN, зависает. [РУКАМИ] У вас
   `all=1`, `wlan0=2` (итог loose, работает), но на другом дистрибутиве может быть иначе. Нужно проверять
   `net.ipv4.conf.<iface>.rp_filter` перед стартом TUN и предупреждать.
3. **Метрика.** Маршрут Xray имеет метрику 1. Если у физического маршрута по умолчанию метрика 0, он выигрывает, и
   TUN молча не работает. [РУКАМИ] Обычно у NetworkManager/DHCP 100 и выше.
4. **`freedom` на сервере блокирует собственные адреса и приватные диапазоны** (`blocked by a finalrule`). Для реального
   сервера это защита, трогать её не надо (docs/server-notes.md). Для лаборатории разрешено.
5. **VLESS без шифрования на публичный IP Xray отвергает** (это же правило уже реализовано в парсере). `encryption`
   (`xray vlessenc`) работает сквозным образом, проверено в петлевом тесте. [РУКАМИ]
6. **Текст ошибок блокировки рукопожатия виден только на уровне `info`.** Клиент пишет
   `proxy/vless/outbound: failed to find an available destination > common/retry: [EOF]`, а сервер
   `REALITY: processed invalid connection ... handshake did not complete successfully`. Оба в `[Info]`. При `loglevel=warning`
   (наше умолчание) клиентская сторона эти строки **не показывает**, поэтому эвристика подсказки «попробуйте fp=firefox»
   (по предупреждениям и ошибкам ядра) на живом сервере **молчала бы**. Её надо перенастроить (см. раздел 7, вопрос 6).
   [РУКАМИ на лабораторном случае, не на реальной блокировке]
7. **«Direct» в TUN тоже идёт через стек Xray.** В режиме `include` весь остальной трафик (игры, торренты) проходит через
   пользовательский TCP/IP-стек Xray и аутбаунд `freedom`. Ответы на ping генерирует сам Xray, и это не показывает
   доступность цели [ДОК]. Для чувствительных к задержке игр это стоит замерить на реальном железе. [НЕ ПРОВЕРЕНО]
8. **IPv6.** Если `autoSystemRoutingTable` содержит только `0.0.0.0/0`, IPv6-трафик идёт мимо туннеля (утечка).
   Нужно добавлять `::/0` и IPv6-адрес в `gateway`. [ДОК, НЕ ПРОВЕРЕНО: в лаборатории нет IPv6]

## 4. Варианты

### Вариант A: TUN-инбаунд самого Xray

| | |
|---|---|
| Что умеет | TUN, правила `process` (имя, путь, папка), `self/`, авто-маршруты, привязка исходящих к интерфейсу, UDP, все транспорты Xray (включая XHTTP), Windows: WFP-фильтры утечек, DNS на интерфейсе |
| Чего не умеет | `process` на macOS. Автонастройка DNS на Linux только через systemd-resolved. Документация по связке process+TUN скудная |
| Бинарники | один: `xray` (35 МБ). Windows: `xray.exe` + `wintun.dll` (оба в официальном zip) |
| Права | Linux: `CAP_NET_ADMIN` или root. Windows: администратор [ДОК] |
| Установка | как сейчас: пользователь кладёт `xray` и `.dat` (на Windows ещё `wintun.dll`), приложение ничего не ставит |
| Риски | `rp_filter`; метрика; VPS-домен; DNS на не-systemd-resolved; поведение при сне и смене сети; Windows целиком не проверялась; TUN в Xray сравнительно молодая функция |
| Проверено | Linux: TCP, UDP, `process` в обоих режимах, защита от петли, Reality+Vision, очистка после `kill -9` |

### Вариант B: sing-box как TUN-слой перед Xray

| | |
|---|---|
| Что умеет | TUN (`auto_route`, `strict_route`, `auto_redirect` на nftables), `process_name`, `process_path`, `process_path_regex` на Linux, Windows, macOS, политика маршрутов на Linux (`ip rule` 9000-9003, таблица 2022), маршрут вне `default` |
| Чего не умеет | XHTTP; нужен Xray как отдельный второй процесс (socks-инбаунд) |
| Бинарники | `sing-box` (81 МБ) и `libcronet.so` (12 МБ) на Linux, плюс `xray`. Windows: `sing-box.exe` + wintun (по документации sing-box про wintun не сказано) [НЕ ПРОВЕРЕНО] |
| Права | то же самое |
| Защита от петли | **вручную**: правило `process_name: xray -> direct` (или IP VPS), `auto_detect_interface`. Без правила режим `exclude` ломается. [РУКАМИ] |
| Риски | два процесса и два конфига, синхронизация правил в двух форматах (в SPEC этап 7 уже это предполагал), больше размер, ещё один бинарник у пользователя, нестабильность версий (в доке уже 1.15, опции переименовываются) |
| Проверено | Linux: TCP, UDP, `process_name` в `include` и `exclude`, цепочка до Reality+Vision, петля без правила |

### Вариант C: прочее

- **mihomo (Clash.Meta)** как TUN-слой: по идее то же, что B, и так же второй процесс. [НЕ ПРОВЕРЕНО, только по общим знаниям]
- **tun2socks** (без правил по процессам) плюс политика маршрутов ОС: на Linux можно через `cgroup`/`uid` и `fwmark`, на Windows это WFP.
  Ближе к «писать самим», много платформенного кода. Не рекомендую. [НЕ ПРОВЕРЕНО]
- **Windows**: сторонние решения (Proxifier-подобные драйверы) уже закрывают «по процессу», но это не наш стек.

## 5. Что именно это значит для этапа 5.2

Если вы утвердите вариант A:

- В `tun/backend.rs` один бэкенд (`XrayTun`), интерфейс допускает второй (`SingBoxTun`) позже.
- Конфиг Xray получает TUN-инбаунд (`name`, `gateway` IPv4 и IPv6, `autoSystemRoutingTable`, `autoOutboundsInterface: auto`,
  sniffing), правила `process` из пользовательских и пресетов в режимах `include` и `exclude`, правило `network=udp, port=443 -> block`
  (пресет QUIC) для серверов без Vision.
- Адрес VPS резолвится приложением заранее, в аутбаунд идёт IP.
- Предстартовые проверки: наличие `/dev/net/tun` (Linux) или `wintun.dll` (Windows), права, `rp_filter`,
  метрика маршрута по умолчанию, понятные сообщения вместо `operation not permitted`.
- Очистка: Xray убирает интерфейс и маршруты сам. Приложение пишет в `state.json`, что TUN поднят, и при старте
  проверяет остатки (на Linux: интерфейс, маршрут, при DNS-режиме `resolvectl revert`).
- В режиме TUN системный прокси не включается (уже так в этапе 4).

## 6. Рекомендация

**Вариант A (TUN самого Xray) как основной на обеих ОС.** Причины: один процесс и один бинарник (как сейчас), одна
система правил, поддерживается XHTTP, защита от петли и WFP-защита от утечек встроены, Windows-поддержка заявлена
в документации, а Linux проверен практически на всех критичных сценариях. Варианта B это не отменяет: если на
Windows `process` в TUN окажется ненадёжным, то sing-box подключается как второй бэкенд за тем же интерфейсом.

Главные риски этого выбора (по убыванию): Windows целиком не проверена; живой Discord не проверен; DNS в режиме
`include` для заблокированных доменов; поведение при сне и смене сети; `rp_filter` на нестандартных дистрибутивах.

## 7. Вопросы к вам

1. **Утверждаете вариант A как основной?** B оставляем запасным (не реализуем сейчас)?
2. **Права на Linux**: запуск `sudo elf-gate --tun` (как в SPEC) или `setcap cap_net_admin+ep` на копию `xray` в папке
   приложения? Второе удобнее, но любой процесс, запущенный с этим бинарником, получает capability. Что предпочитаете?
3. **`rp_filter`**: при строгом режиме только предупреждать (и подсказывать `sysctl`) или приложение само ставит loose на время работы TUN?
4. **Адрес VPS**: согласны, что приложение резолвит домен само перед стартом TUN и подставляет IP в аутбаунд?
5. **DNS в режиме `include` (только Discord)**: системный DNS не трогаем (рекомендую) и полагаемся на sniffing плюс
   резолв на сервере, либо включаем `autoSystemDnsToGateway` (Linux) и `dns` + WFP (Windows) и гоним весь DNS в туннель?
   Второе ломает «российские сайты напрямую» из пресета `ru-direct` без отдельных правил DNS.
6. **Подсказка про fp**: клиентские ошибки рукопожатия пишутся на уровне `info`. Поднять `loglevel` ядра до `info`
   (больше шума в логах), либо ловить признак иначе (например, фоновая проверка соединения до VPS)? Эвристика из прошлой
   доработки на живой блокировке сейчас, скорее всего, молчала бы.
7. **Windows**: у вас есть машина или виртуалка для проверок? Без неё код TUN для Windows пойдёт в репозиторий
   непроверенным, и в `docs/windows-checklist.md` останется полный список. Это допустимо?
8. **Состав процессов Discord** для пресета `discord-only`: на Windows `Discord.exe`, `DiscordPTB.exe`, `DiscordCanary.exe`;
   на Linux `Discord`, `vesktop` и другие. Какой клиент у вас реально (Discord, Vesktop, Flatpak)? От этого зависят имена.
9. **Режим `exclude` по умолчанию** и **QUIC**: достаточно ли, что при Vision QUIC блокируется самим Xray, а правило
   `block udp/443` добавляется из пресета для остальных серверов?

## 10. Дополнение этапа 5.2: что выяснилось при реализации

Метки те же: **[РУКАМИ]** проверено на Linux в лаборатории (сценарии 06 и 07, настоящий `elf-gate`), **[НЕ ПРОВЕРЕНО]**.

1. **DNS по доменам правил через туннель работает** [РУКАМИ]. Запросы системного резолвера к его вышестоящему серверу
   попадают в TUN; правило `udp/53 из tun-in -> dns-out` отдаёт их DNS-модулю Xray, который выбирает резолвер по домену.
   `include`: домены из списка идут к публичному резолверу через туннель (запрос выходит со стороны VPN-сервера),
   остальные к вышестоящему системному напрямую. `exclude` наоборот. Ловушка: резолвер «по умолчанию» не должен иметь
   `skipFallback`, иначе он не используется для неперечисленных имён. Системный DNS не меняется.
   Не проверено: DNS поверх TCP (в правило включён только UDP), DoH/DoT приложений. [НЕ ПРОВЕРЕНО]
2. **`geoip:private` шире, чем «домашняя сеть»** [РУКАМИ, по `geoip.dat`]: в нём `100.64.0.0/10` (CGNAT, Tailscale),
   `198.18.0.0/15` (адреса нашего TUN-шлюза) и документационные `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`.
   Пресет `local-direct` отправляет всё это напрямую. В лаборатории это пришлось учесть: её «интернет» это `203.0.113.x`.
3. **Бандл Xray беден наборами** [РУКАМИ]: в `geoip.dat` всего 22 набора (есть `ru` и `private`, нет `ua`), в `geosite.dat`
   нет `category-ua`. Xray не запускается, если правило называет отсутствующий набор. Поэтому elf-gate читает `.dat`, пропускает
   такие правила с предупреждением (по ТЗ), остальные правила работают. Пресет `ua-direct` с этими файлами пуст.
4. **Ядро с `cap_net_admin` не умирает вместе с elf-gate** [РУКАМИ + `man 2const PR_SET_PDEATHSIG`]: при запуске файла с
   capabilities ядро Linux сбрасывает `PDEATHSIG`. После `kill -9 elf-gate` TUN остался бы поднятым. Решение: сторож
   `elf-gate --supervise`, которому ядро шлёт `SIGTERM` и который останавливает Xray. Проверено: kill родителя убирает
   ядро и интерфейс. В пути через `sudo` (root) сторож не нужен. Ядро без `PDEATHSIG` ловится ещё и при следующем запуске
   (`state.json`).
5. **`xray run -test` проверяет TUN-конфиги без прав** [РУКАМИ]: интерфейс не создаётся, поэтому проверку итогового
   конфига можно делать до запуска и показывать текст Xray.
6. **Проверка соединения идёт мимо пользовательских правил** [РУКАМИ]: служебный домен `connectivitycheck.gstatic.com` из
   socks-инбаунда всегда уходит в аутбаунд `proxy`, иначе в `include` проверка прошла бы напрямую и ничего не доказывала.
   В лаборатории проверка проходит через VPN («трафик идёт через сервер»).
7. **Сквозной тест поймал дефект** [РУКАМИ]: режим `--supervise` не был подключён в `main`. Теперь покрыт сценарием 07.

Результаты сценария 07 (настоящий `elf-gate`, 39 проверок, 0 сбоев): [docs/tun-research/lab/RESULTS.txt](tun-research/lab/RESULTS.txt).
Что не проверено в 5.2: Windows целиком (UAC и `ShellExecuteW`, Wintun, WFP, `GetAdaptersAddresses`, список процессов), настоящий
Discord, путь `setcap` (нужен root; логика проверена мок-хостом и сторожем), поведение при сне и смене сети.
