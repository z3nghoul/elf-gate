## Этап 6

### Кеш `xray run -test` (6.1)
- Ключ кеша: FNV-1a (64 бит) от JSON сгенерированного конфига (ключи объектов `serde_json` отсортированы, поэтому
  хеш стабилен). Криптостойкость не нужна: вход создаём мы сами, атакующего у кеша нет. Отвергнуто: крейт `sha2`
  (лишняя зависимость ради ключа кеша), `DefaultHasher` (не гарантирует стабильность между версиями Rust).
- Версия Xray = первая строка `xray version`; при смене версии кеш сбрасывается целиком.
- Файл `check-cache.json` лежит в каталоге состояния (не в `state.json`): `state.json` читают и пишут пути аварийной
  очистки, смешивать с большим кешем незачем. В кеш попадают только вердикты Xray (принят / отвергнут с причиной);
  «не удалось запустить» не кешируется.
- Параллелизм: общий `Semaphore(4)` в `Checker`; проверка перед подключением идёт через тот же `Checker`.
- «Перепроверка только изменившихся серверов» получается сама: после обновления подписки у неизменных серверов
  тот же конфиг, значит тот же ключ.

### Подписки и HTTP-клиент (6.2)
- `reqwest` 0.13 без нативного TLS на Linux (rustls, как в SPEC), а **на Windows с `native-tls` (SChannel)**.
  Причина: rustls тянет `aws-lc-sys`, которому нужен C-компилятор целевой платформы; без `mingw-w64`
  проверка `cargo check/clippy --target x86_64-pc-windows-gnu` на Linux не проходит, а правило проекта требует
  clippy под Windows-таргет. SChannel без C-сборки, плюс использует системное хранилище сертификатов. Фичи `socks`
  нужны для URL-пинга через локальный socks. Отвергнуто: `ring` (тоже C-код), установка mingw (трогает систему).
- `base64` — для тела подписки и заголовка `profile-title`.
- Клиент подписок всегда `no_proxy()`: запрос идёт напрямую в любом режиме. В TUN трафик самого процесса уводится из
  туннеля правилом `process: [elf-gate, elf-gated] -> direct` (оно в конфиге TUN всегда, до пользовательских правил).
- Список серверов подписки кешируется в `subscriptions.json` рядом с `config.toml`: при старте список есть без сети,
  неудачное обновление ничего не меняет. Дата обновления хранится там же.
- При обновлении серверы с тем же `имя|хост:порт` сохраняют runtime-id, поэтому активное подключение и выделение
  не теряются; `[[overrides]]` привязаны к тому же ключу.
- Авто-обновление: проверка раз в минуту, по `auto_update_hours` (0 = выключено); после ошибки повтор не раньше чем
  через 10 минут.
- Новая подписка добавляется в `config.toml` только после успешной первой загрузки. Имя: `profile-title`, иначе хост.

### Пинг и автоперебор fp (6.3, 6.4)
- TCP-пинг: до 16 одновременно. URL-пинг и перебор fp: временное ядро на случайных портах (свой файл конфига
  `probe-<pid>-<n>.json`, удаляется), запрос через `socks5h` средствами `reqwest`, общий лимит 4 ядра.
- В режиме TUN при активном подключении URL-пинг заменяется TCP-пингом (с пометкой в строке статуса): соединение
  временного ядра с сервером попало бы в туннель. TCP-пробы идут из процесса elf-gate, он выведен из туннеля правилом.
- Автоперебор fp запускается в двух случаях: URL-пинг не прошёл, а TCP прошёл; проверка соединения после подключения
  в PROXY-режиме не прошла. Порядок: firefox, chrome, safari, ios, edge, random, qq; побеждает первый по порядку
  среди успешных (все 7 запускаются с лимитом 4, а не по одному: быстрее при редких успехах).
- Найденный fp применяется сразу как переопределение с пометкой `fp_auto = true` (не только «предлагается»: пользователь
  в этот момент может отсутствовать), ссылка не меняется; активное подключение перезапускается с новым fp.
- Результат (в том числе «ничего не помогло») кешируется по серверу вместе с версией Xray (`fp_auto_xray`): повторный
  перебор только при смене версии. Вручную выбранный fp (без `fp_auto`) перебор не затрагивает никогда.
- В TUN-режиме перебор не запускается (те же причины, что у URL-пинга); остаётся подсказка про fp=firefox.

### Основной / запасной сервер (6.5)
- Роль (`primary` / `backup`) хранится в `[[overrides]]` (`role`), назначается клавишей `b`; по одному серверу на роль,
  новое назначение снимает роль со старого. Автопереключение включается, когда пользователь подключается к основному
  и запасной назначен (подключение к запасному напрямую парой не считается).
- Реализация в Xray: два аутбаунда `proxy-primary` / `proxy-backup`, балансировщик `proxy` (`selector=[proxy-primary]`,
  `fallbackTag=proxy-backup`, `leastPing`) и обычный `observatory`; все правила, которые вели на аутбаунд `proxy`,
  ведут на балансировщик; в режиме exclude добавлено последнее правило `tcp,udp -> balancer`, иначе трафик без правил
  пошёл бы только на основной (первый аутбаунд).
- Проверено реальным Xray (integration test в `xray::integration_tests`): основной умирает, трафик уходит на запасной,
  основной возвращается сам.
- **`burstObservatory` не подошёл:** его минимальный интервал 10 с (меньшее значение Xray поднимает сам), а связка
  `leastLoad` + `fallbackTag` в эксперименте не переключалась на запасной после отказа основного. Обычный
  `observatory` с `leastPing` переключается и возвращает.
- **Гистерезиса «N чистых проверок подряд» в Xray нет.** Демпфирование даёт интервал проверок (10 с): основной
  отбрасывается после одной неудачной проверки и возвращается после следующей удачной, чаще раза в интервал не
  дёргается. Строгий гистерезис потребовал бы читать состояние observatory через gRPC и самому переключать
  соединение; отложено, записано в `docs/open-questions.md`.
- Если запасной недоступен при подъёме TUN (домен не резолвится), он пропускается с предупреждением в логе.

### Фрагментация ClientHello (стартовала на этапе 6, UI и пресеты этапа 7)
- Способ: `freedom`-аутбаунд `fragment` (`packets=tlshello`, `length=100-200`, `interval=10-20`) и
  `streamSettings.sockopt.dialerProxy = "fragment"` у аутбаунда сервера. Это единственный путь, который работает для
  VLESS-аутбаунда (настройка `fragment` у самого `freedom` режет только его собственный трафик).
- Опция на сервер (`fragment` в `[[overrides]]`, клавиша `z`), по умолчанию выключена, только для TLS и Reality.

## Этап 7

- Экран правил, генерация правил, валидация, пресеты и подтверждение перезапуска были готовы в 5.2; на этапе 7 добавлено
  недостающее: `ProxyOverride` (см. ниже), `ua-direct`, пометки про QUIC, проверка имён процессов.
- **`ProxyOverride` в PROXY-режиме:** в список обхода системного прокси добавляются простые домены (`domain:x` как
  `x` и `*.x`, `full:x` как `x`) и IPv4-адреса (одиночные и сети /8, /16, /24 как `a.*`) из правил «напрямую» и
  включённых пресетов. Только в режиме `exclude`: в `include` перечисленное должно идти *через* прокси. `keyword:`,
  geosite/geoip и прочие CIDR выразить в списке обхода нельзя, их по-прежнему решает маршрутизация Xray. При изменении
  правил список отправляется повторно (повторное включение прокси не теряет исходные настройки пользователя).
- **`ua-direct`:** в имеющихся `geoip.dat`/`geosite.dat` нет `geoip:ua` и `geosite:category-ua`, поэтому пресет задан
  списком доменов (зона `.ua`, `ukr.net`, `1plus1.video`, `privat24.ua`, `monobank.ua`), по IP не работает; пометка есть
  в названии пресета и в строке подсказки. Если в будущей сборке Xray наборы появятся, их можно вернуть в `presets.toml`.
- **`block-quic`:** по умолчанию выключен (как решено пользователем; в `plan-additions.md` раньше стояло «включён»).
  При `flow=xtls-rprx-vision` UDP/443 уже закрыт ядром: об этом строка `QUIC:` в деталях сервера и первая фраза
  подсказки пресета, когда выбран/подключён такой сервер.
- **Имена процессов Linux:** проверены на машине разработки (Arch): `Discord` (Flatpak: `/app/discord/Discord`),
  `steam`, `steamwebhelper` подтверждены; `vesktop-bin` из Arch запускается через системный Electron (процесс `electron44`),
  имя `vesktop` для него неверно (оставлено для AppImage/Flatpak, помечено в `presets.toml`); `deluge` это Python
  (`python3.x`), помечен как вероятно неверный; остальное не проверено и помечено комментарием.

### Уточнения после этапа 7

## Этап 8
- Статистика: `stats`/`api`/`policy` и dokodemo-инбаунд `api` добавляются в каждый конфиг основного ядра (`api_port = 0`
  выключает; временные ядра пинга его выключают, чтобы не занимать порт). Опрос раз в секунду через
  `xray api statsquery`, показ: скорость и итоги отдельно для VPN и напрямую (`proxy-primary`/`proxy-backup` считаются как VPN).
  Счётчик uplink короткого запроса может прочитаться как 0 (проверено реальным Xray), поэтому тест проверяет downlink.
- Экран настроек: каждая строка = команда `Cmd::Set`, значения проверяет и сохраняет фоновая часть; порты и пути
  применяются при следующем подключении. Включены переключатели `auto_connect` и автозапуска (бэкенды этапа 6).
- Темы: `dark` и `light` (`[ui].theme`).
- Автопинг: `[ping].auto_interval_secs` (60 по умолчанию, 0 = выкл), TCP, без мигания «...»; без открытого интерфейса интервал
  растёт в 5 раз, не более 300 с. Ручной `p` сбрасывает таймер. У значения есть возраст замера («42 ms, 30 с назад», в деталях).
- **Задержка активного сервера:** берётся не из observatory (у Xray нет CLI для `ObservatoryService`, а тянуть gRPC ради
  одной цифры не стали), а из той же проверки соединения через туннель (`generate_204` через socks), на каждом цикле автопинга.

## Пинг: тип замера и устойчивость (после этапа 8)
- Жалоба: пинг прыгал между ~40 и ~200 мс. Причина: один TCP-connect (холодный DNS/ARP, первые пакеты) и URL-замер, в который
  входили запуск временного Xray, TCP до сервера и рукопожатия.
- TCP-пинг: один прогревочный connect (отбрасывается) и 3 замера подряд, показывается медиана (с паузой 80 мс).
- URL-пинг: прогревочный запрос не засчитывается, затем 3 запроса по уже открытому соединению через туннель, медиана.
  Запуск временного ядра и установка соединения до сервера в замер не входят.
- Проверка соединения активного сервера теперь тоже мерит только запрос (часы стартуют после socks-рукопожатия).
- В UI рядом со значением тип замера: в списке `tcp` / `vpn`, в деталях «TCP до сервера» / «через туннель» плюс возраст замера.
  Автопинг и `p` дают `tcp`; URL-режим и задержка активного сервера дают `vpn`.

## Ассеты TUN-копии ядра (Linux)
- Ядро всегда запускается с явным `XRAY_LOCATION_ASSET` (`process::asset_dir`: рядом с бинарником, а для симлинка рядом с реальным
  файлом); это относится и к проверке `run -test`, и к запуску, и к временным ядрам.
- Перед запуском TUN проверяется, что рядом с копией ядра лежат `geoip.dat` и `geosite.dat` (иначе блокирующая проблема с командами установки).
  elf-gate сам их не копирует (sudo не вызывает): это делают `install_commands` и `packaging/scripts/elf-gate-tun.sh`, который
  теперь ставит оба файла и обновляет их, если исходники в `bin/` изменились.
- При старте ядра в журнал пишется строка с путём к xray и к ассетам (и есть ли файлы); та же строка добавляется к ошибке
  «Xray отверг итоговый конфиг». Сообщение «ядро Xray не найдено» теперь перечисляет, где искали.

### Дочерний xray не видит geoip.dat (Linux, TUN)
- В коде elf-gate нет `unshare`, `chroot`, namespace, seccomp, `env_clear`, `systemd-run`/`bwrap`: у ядра та же ФС, что у родителя
  (проверено чтением кода: единственный `pre_exec` ставит `PDEATHSIG`). Причина на стороне окружения/способа запуска не найдена
  по коду, поэтому добавлены автоповтор и отчёт.
- `validate::check_config`: если отказ «окруженческий» (stat/no such file/permission denied/geoip/geosite), проверка повторяется
  «как из shell» (без `XRAY_LOCATION_ASSET`, cwd = каталог ядра). Если так проходит, ядро дальше запускается тем же способом
  (в журнал пишется предупреждение). Если не проходит, отказ содержит полный вывод xray, вывод повтора и отчёт: argv, cwd,
  PATH/HOME/XDG_RUNTIME_DIR, container/flatpak, что видит родитель (`geoip.dat: N байт` или ошибка), `NoNewPrivs`, `Seccomp`,
  `CapEff/CapBnd`, mount namespace, корень, метка LSM. То же пишется в `elf-gated.log`.
- Такие отказы не кешируются (они ничего не говорят о конфиге).

## TUN на Linux: петля, определение процесса, шум (после жалобы пользователя)
- **Петля к адресу VPN-сервера.** Источник: соединения с `198.18.0.1` (адрес TUN) к IP сервера создаёт сам `elf-gated`: фоновый
  TCP-пинг всех серверов (раз в 60 с) и ручной `p`. Правило «процесс elf-gate -> direct» их не спасало, потому что определение
  процесса не работало («no process found for inode»), и пакеты уходили в `proxy` (VPN внутри VPN). Свои сокеты Xray уже привязаны
  к физическому интерфейсу (`autoOutboundsInterface: auto`) и петли не создают. Исправление не зависит от определения процесса:
  в TUN-конфиг добавлены правила `ip -> direct` для адресов ВСЕХ серверов списка (резолвятся до подъёма туннеля) и `domain full: -> direct`
  для их имён и хостов подписок, выше пользовательских правил. `sockopt.mark` + `ip rule` не взяты: правила маршрутизации ядра требуют
  прав, которых у копии ядра (только `cap_net_admin`) нет, а elf-gate sudo не вызывает. Для Windows те же правила работают (одна и та же
  генерация конфига; `autoOutboundsInterface` тоже включён).
- **«no process found for inode 0 / N».** Устранение петли не лечит определение процесса: оно связано с правами ядра. Inode 0 бывает у
  сокетов без владельца (например, TIME_WAIT), ненулевые inode с ошибкой - у процессов, чьи `/proc/<pid>/fd` ядро читать не может.
  Для программ другого пользователя и песочниц нужны `cap_sys_ptrace` и `cap_dac_read_search`. **Результат проверки этой гипотезы
  на машине пользователя в задании не приведён (стояла заглушка)**, поэтому права НЕ выдаются по умолчанию: `ELF_GATE_FULL_CAPS=1
  ./elf-gate-tun.sh` и подсказка `setcap ...` включают их добровольно, в README описано, что они дают. Если в правилах есть
  процессы, а у ядра этих прав нет (`getcap`), при подключении один раз показывается предупреждение (не ошибка).
  Соединения с неопределённым процессом Xray пускает по правилу по умолчанию; шум от его сообщений схлопывается (см. ниже).
- **Шум.** Консольный access-лог Xray включён по умолчанию, если `log.access` не задан; теперь `access: "none"`. Настройка
  «Подробный лог ядра (access)» (`[core].verbose_log`, экран настроек) возвращает access-строки и уровень `info`. Повторяющиеся строки ядра
  (по тексту без чисел) показываются один раз, остальные считаются: «… (ещё N раз)» после окна 10 с.
- **Кеш проверок.** Отказы по причине окружения не кешируются, а такие записи старого файла удаляются при загрузке (причина
  прошлой проблемы с `check-cache.json`).

## Подписки: HWID и JSON-конфиги Xray (Remnawave и подобные)
- **HWID.** `x-hwid` = первые 16 hex от `sha256(machine-id)` (Linux `/etc/machine-id`, Windows `MachineGuid`; запасной вариант: случайное
  значение из часов и PID), создаётся один раз, хранится в `[device].hwid` и одинаково уходит во все подписки. Вместе с ним:
  `x-device-os` (Linux/Windows), `x-ver-os` (VERSION_ID / сборка Windows), `x-device-model: elf-gate`. User-Agent по умолчанию для новых
  подписок `v2rayNG/1.10.4` (существующие подписки сохраняют свой). HWID виден на экране настроек с пояснением, что он занимает слот
  подписки. Новая зависимость `sha2` (sha256 для HWID; для ключа кеша проверок по-прежнему обходимся FNV-1a).
- **JSON-подписка** = массив полных конфигов Xray. Запись целиком хранится как «ссылка» `xrayjson:<json>` (так работает кеш подписок и
  `parse_link`), в интерфейс уходит копия без outbounds (там ключи). Тип сервера «готовый конфиг» (`Server.full`).
- **Цепочки.** Один outbound брать нельзя: `proxy` ходит через следующий узел по `streamSettings.sockopt.dialerProxy` (в старых конфигах
  `proxySettings.tag`), а тот через следующий (в вашем случае последним звеном стоит `freedom` с `fragment`). Берутся входной outbound и
  всё, до чего он дотягивается по этим ссылкам, остальное отбрасывается. Входной = последнее «безусловное» правило провайдера
  (`outboundTag`/`balancerTag`), иначе outbound с тегом `proxy`, иначе первый прокси. Если вход это балансировщик: переносятся он,
  его `selector`-outbounds и `observatory`/`burstObservatory`.
- **Что меняется при сборке.** Теги: вход становится `proxy` (балансировщик тоже `proxy`), остальные получают префикс `pv-`, ссылки
  `dialerProxy`, `selector`, `fallbackTag`, `subjectSelector` поправлены. Наши inbounds/api/stats/правила/DNS остаются, провайдерские
  `routing` и `dns` не копируются. Содержимое outbound (gRPC, Reality, fragment и т.д.) не трогается, **с одним исключением**: Xray 26
  удалил `proxySettings` («migrated to streamSettings.sockopt.dialerProxy»), поэтому он переписывается в `dialerProxy` (проверено
  `xray run -test`).
- **TUN.** Имена всех узлов цепочки резолвятся до подъёма туннеля и подставляются как адреса (имя остаётся как serverName, если его не
  было); все они и их IP попадают в список «мимо туннеля». TCP-пинг и защита от петли используют первый узел цепочки (конец цепочки
  dialerProxy: именно туда машина подключается первой). URL-пинг и проверка соединения идут через всю цепочку (временное ядро с
  тем же конфигом).
- **Заглушки и заголовки.** Нулевой UUID, адрес `0.0.0.0`/`::`, порт 0 или 1 в любом формате (ссылка или JSON), а также записи без
  прокси-outbound (разделители) это строки-сообщения (`info_only`): показываются приглушённо, Enter показывает пояснение, ни пинга,
  ни проверок, ни подключения.
- Для готовых конфигов недоступны fp, фрагментация и роли основной/запасной (цепочка переносится как есть).

## Кеш проверок: ключ и срок
- Ключ записи = хеш конфига + отпечаток окружения (путь, размер и mtime xray, размер и mtime `geoip.dat`/`geosite.dat`) + версия
  Xray (весь файл). Любое изменение делает записи недействительными. Отказы живут не дольше суток, принятия без срока.
  Формат файла 2; файл старого формата отбрасывается.

## Права копии ядра по умолчанию (Linux)
- Проверено пользователем: с `cap_net_admin,cap_sys_ptrace,cap_dac_read_search` ошибки «no process found» исчезают полностью. Эти три
  права теперь выдаются по умолчанию (`install_commands`, подсказки, `elf-gate-tun.sh`, README); `ELF_GATE_FULL_CAPS=0` оставляет
  только `cap_net_admin`. При урезанных правах строки «no process found» скрываются, одно предупреждение при подключении остаётся.

## Удаление серверов и подписок (баг)
- **Причина «вернулось после перезапуска».** Удаление сервера из подписки меняло только память демона: конфиг не писался, а список
  подписки при старте читается из `subscriptions.json` (и обновляется с панели), поэтому сервер появлялся снова. Воспроизведено тестом.
  Отдельной причины, по которой нельзя удалить пустую подписку, найти не удалось: на текущем коде (и в тесте для пустой, «все скрыты»,
  «только заглушки» и «ошибка загрузки») удаление работает; если проблема повторится, нужен текст ошибки или состояние экрана.
- **Новая семантика.** Ручной сервер удаляется (как раньше, с записью в `config.toml`). Сервер подписки скрывается: ключ
  `имя|адрес:порт|хеш id` пишется в `[[hidden]]` того же `config.toml`, при обновлении и перезапуске он остаётся скрытым; вернуть:
  `h` на подписке (показывает скрытые серыми), затем `x` на скрытом. Скрытые не пингуются, не проверяются и не попадают в трей.
- **Удаление подписки** работает в любом состоянии и убирает серверы, `[[subscriptions]]`, запись в `subscriptions.json`, `[[hidden]]` и
  `[[overrides]]` этой подписки. Всё делает демон; интерфейс только шлёт `DeleteServer` / `UnhideServer` / `DeleteGroup`.
- Если удаляемый или скрываемый сервер подключён, в подтверждении об этом сказано, и демон сначала отключается (переключение на
  запасной не делается).

## Строка с клавишами (UX)
- Внизу экрана отдельная строка `ui/hints.rs`, которую не перекрывают ни панели, ни диалоги (рисуется последней в своей строке). Она
  строится из той же таблицы `action::BINDINGS`, что обрабатывает клавиши и рисует справку: у биндинга есть `bar` (как писать клавишу),
  `short` (подпись), `prio` (что остаётся в узком окне) и `scopes` (на каких экранах работает). Подписи уточняются по выбранному элементу
  (Enter: подключить / отключить / свернуть / пояснение; x: удалить / скрыть / вернуть / удалить подписку); недоступные клавиши не
  показываются. Всегда в конце `? помощь  q/Q выход`. В диалогах, вводе и фильтре строка показывает их собственные клавиши. Без связи
  с фоновой частью команды не предлагаются.
- Узкое окно: сначала уходят клавиши с большим `prio`, остальное заменяется на `…`; строка не переносится и не длиннее окна.
- Минимальная ширина окна снижена с 80 до 60 колонок (по требованию к снапшоту 60 колонок); меньше окна по-прежнему показывается
  сообщение «Увеличьте окно», и под ним тоже строка с клавишами.
- Тесты: снапшоты (`insta`, `src/ui/snapshots/*hint_tests*`) для 27 экранов и состояний; проверки, что показанные клавиши действительно
  вызывают те же действия по таблице, что подсказки зависят от элемента и что узкая строка не переполняется.
