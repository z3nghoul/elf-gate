## Этап 6

### Кеш `xray run -test` (6.1)
- Ключ кеша: FNV-1a (64 бит) от JSON сгенерированного конфига (ключи объектов `serde_json` отсортированы, поэтому
  хеш стабилен). Криптостойкость не нужна: вход создаём мы сами, атакующего у кеша нет. Отвергнуто: крейт `sha2`
  (лишняя зависимость ради ключа кеша), `DefaultHasher` (не гарантирует стабильность между версиями Rust).
- Версия Xray = первая строка `xray version`; при смене версии кеш сбрасывается целиком.
- Файл `check-cache.json` лежит в каталоге состояния (не в `state.json`): `state.json` читают и пишут пути аварийной
  очистки, смешивать с большим кешем незачем. В кеш попадают только вердикты Xray (принят / отвергнут с причиной);
  «не удалось запустить» не кешируется.
- Параллелизм: общий `Semaphore(4)` в `Checker`; проверка перед подключением идёт через тот же `Checker`.
- «Перепроверка только изменившихся серверов» получается сама: после обновления подписки у неизменных серверов
  тот же конфиг, значит тот же ключ.

### Подписки и HTTP-клиент (6.2)
- `reqwest` 0.13 без нативного TLS на Linux (rustls, как в SPEC), а **на Windows с `native-tls` (SChannel)**.
  Причина: rustls тянет `aws-lc-sys`, которому нужен C-компилятор целевой платформы; без `mingw-w64`
  проверка `cargo check/clippy --target x86_64-pc-windows-gnu` на Linux не проходит, а правило проекта требует
  clippy под Windows-таргет. SChannel без C-сборки, плюс использует системное хранилище сертификатов. Фичи `socks`
  нужны для URL-пинга через локальный socks. Отвергнуто: `ring` (тоже C-код), установка mingw (трогает систему).
- `base64` — для тела подписки и заголовка `profile-title`.
- Клиент подписок всегда `no_proxy()`: запрос идёт напрямую в любом режиме. В TUN трафик самого процесса уводится из
  туннеля правилом `process: [elf-gate, elf-gated] -> direct` (оно в конфиге TUN всегда, до пользовательских правил).
- Список серверов подписки кешируется в `subscriptions.json` рядом с `config.toml`: при старте список есть без сети,
  неудачное обновление ничего не меняет. Дата обновления хранится там же.
- При обновлении серверы с тем же `имя|хост:порт` сохраняют runtime-id, поэтому активное подключение и выделение
  не теряются; `[[overrides]]` привязаны к тому же ключу.
- Авто-обновление: проверка раз в минуту, по `auto_update_hours` (0 = выключено); после ошибки повтор не раньше чем
  через 10 минут.
- Новая подписка добавляется в `config.toml` только после успешной первой загрузки. Имя: `profile-title`, иначе хост.

### Пинг и автоперебор fp (6.3, 6.4)
- TCP-пинг: до 16 одновременно. URL-пинг и перебор fp: временное ядро на случайных портах (свой файл конфига
  `probe-<pid>-<n>.json`, удаляется), запрос через `socks5h` средствами `reqwest`, общий лимит 4 ядра.
- В режиме TUN при активном подключении URL-пинг заменяется TCP-пингом (с пометкой в строке статуса): соединение
  временного ядра с сервером попало бы в туннель. TCP-пробы идут из процесса elf-gate, он выведен из туннеля правилом.
- Автоперебор fp запускается в двух случаях: URL-пинг не прошёл, а TCP прошёл; проверка соединения после подключения
  в PROXY-режиме не прошла. Порядок: firefox, chrome, safari, ios, edge, random, qq; побеждает первый по порядку
  среди успешных (все 7 запускаются с лимитом 4, а не по одному: быстрее при редких успехах).
- Найденный fp применяется сразу как переопределение с пометкой `fp_auto = true` (не только «предлагается»: пользователь
  в этот момент может отсутствовать), ссылка не меняется; активное подключение перезапускается с новым fp.
- Результат (в том числе «ничего не помогло») кешируется по серверу вместе с версией Xray (`fp_auto_xray`): повторный
  перебор только при смене версии. Вручную выбранный fp (без `fp_auto`) перебор не затрагивает никогда.
- В TUN-режиме перебор не запускается (те же причины, что у URL-пинга); остаётся подсказка про fp=firefox.
