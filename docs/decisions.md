## Этап 6

### Кеш `xray run -test` (6.1)
- Ключ кеша: FNV-1a (64 бит) от JSON сгенерированного конфига (ключи объектов `serde_json` отсортированы, поэтому
  хеш стабилен). Криптостойкость не нужна: вход создаём мы сами, атакующего у кеша нет. Отвергнуто: крейт `sha2`
  (лишняя зависимость ради ключа кеша), `DefaultHasher` (не гарантирует стабильность между версиями Rust).
- Версия Xray = первая строка `xray version`; при смене версии кеш сбрасывается целиком.
- Файл `check-cache.json` лежит в каталоге состояния (не в `state.json`): `state.json` читают и пишут пути аварийной
  очистки, смешивать с большим кешем незачем. В кеш попадают только вердикты Xray (принят / отвергнут с причиной);
  «не удалось запустить» не кешируется.
- Параллелизм: общий `Semaphore(4)` в `Checker`; проверка перед подключением идёт через тот же `Checker`.
- «Перепроверка только изменившихся серверов» получается сама: после обновления подписки у неизменных серверов
  тот же конфиг, значит тот же ключ.

### Подписки и HTTP-клиент (6.2)
- `reqwest` 0.13 без нативного TLS на Linux (rustls, как в SPEC), а **на Windows с `native-tls` (SChannel)**.
  Причина: rustls тянет `aws-lc-sys`, которому нужен C-компилятор целевой платформы; без `mingw-w64`
  проверка `cargo check/clippy --target x86_64-pc-windows-gnu` на Linux не проходит, а правило проекта требует
  clippy под Windows-таргет. SChannel без C-сборки, плюс использует системное хранилище сертификатов. Фичи `socks`
  нужны для URL-пинга через локальный socks. Отвергнуто: `ring` (тоже C-код), установка mingw (трогает систему).
- `base64` — для тела подписки и заголовка `profile-title`.
- Клиент подписок всегда `no_proxy()`: запрос идёт напрямую в любом режиме. В TUN трафик самого процесса уводится из
  туннеля правилом `process: [elf-gate, elf-gated] -> direct` (оно в конфиге TUN всегда, до пользовательских правил).
- Список серверов подписки кешируется в `subscriptions.json` рядом с `config.toml`: при старте список есть без сети,
  неудачное обновление ничего не меняет. Дата обновления хранится там же.
- При обновлении серверы с тем же `имя|хост:порт` сохраняют runtime-id, поэтому активное подключение и выделение
  не теряются; `[[overrides]]` привязаны к тому же ключу.
- Авто-обновление: проверка раз в минуту, по `auto_update_hours` (0 = выключено); после ошибки повтор не раньше чем
  через 10 минут.
- Новая подписка добавляется в `config.toml` только после успешной первой загрузки. Имя: `profile-title`, иначе хост.

### Пинг и автоперебор fp (6.3, 6.4)
- TCP-пинг: до 16 одновременно. URL-пинг и перебор fp: временное ядро на случайных портах (свой файл конфига
  `probe-<pid>-<n>.json`, удаляется), запрос через `socks5h` средствами `reqwest`, общий лимит 4 ядра.
- В режиме TUN при активном подключении URL-пинг заменяется TCP-пингом (с пометкой в строке статуса): соединение
  временного ядра с сервером попало бы в туннель. TCP-пробы идут из процесса elf-gate, он выведен из туннеля правилом.
- Автоперебор fp запускается в двух случаях: URL-пинг не прошёл, а TCP прошёл; проверка соединения после подключения
  в PROXY-режиме не прошла. Порядок: firefox, chrome, safari, ios, edge, random, qq; побеждает первый по порядку
  среди успешных (все 7 запускаются с лимитом 4, а не по одному: быстрее при редких успехах).
- Найденный fp применяется сразу как переопределение с пометкой `fp_auto = true` (не только «предлагается»: пользователь
  в этот момент может отсутствовать), ссылка не меняется; активное подключение перезапускается с новым fp.
- Результат (в том числе «ничего не помогло») кешируется по серверу вместе с версией Xray (`fp_auto_xray`): повторный
  перебор только при смене версии. Вручную выбранный fp (без `fp_auto`) перебор не затрагивает никогда.
- В TUN-режиме перебор не запускается (те же причины, что у URL-пинга); остаётся подсказка про fp=firefox.

### Основной / запасной сервер (6.5)
- Роль (`primary` / `backup`) хранится в `[[overrides]]` (`role`), назначается клавишей `b`; по одному серверу на роль,
  новое назначение снимает роль со старого. Автопереключение включается, когда пользователь подключается к основному
  и запасной назначен (подключение к запасному напрямую парой не считается).
- Реализация в Xray: два аутбаунда `proxy-primary` / `proxy-backup`, балансировщик `proxy` (`selector=[proxy-primary]`,
  `fallbackTag=proxy-backup`, `leastPing`) и обычный `observatory`; все правила, которые вели на аутбаунд `proxy`,
  ведут на балансировщик; в режиме exclude добавлено последнее правило `tcp,udp -> balancer`, иначе трафик без правил
  пошёл бы только на основной (первый аутбаунд).
- Проверено реальным Xray (integration test в `xray::integration_tests`): основной умирает, трафик уходит на запасной,
  основной возвращается сам.
- **`burstObservatory` не подошёл:** его минимальный интервал 10 с (меньшее значение Xray поднимает сам), а связка
  `leastLoad` + `fallbackTag` в эксперименте не переключалась на запасной после отказа основного. Обычный
  `observatory` с `leastPing` переключается и возвращает.
- **Гистерезиса «N чистых проверок подряд» в Xray нет.** Демпфирование даёт интервал проверок (10 с): основной
  отбрасывается после одной неудачной проверки и возвращается после следующей удачной, чаще раза в интервал не
  дёргается. Строгий гистерезис потребовал бы читать состояние observatory через gRPC и самому переключать
  соединение; отложено, записано в `docs/open-questions.md`.
- Если запасной недоступен при подъёме TUN (домен не резолвится), он пропускается с предупреждением в логе.

### Фрагментация ClientHello (стартовала на этапе 6, UI и пресеты этапа 7)
- Способ: `freedom`-аутбаунд `fragment` (`packets=tlshello`, `length=100-200`, `interval=10-20`) и
  `streamSettings.sockopt.dialerProxy = "fragment"` у аутбаунда сервера. Это единственный путь, который работает для
  VLESS-аутбаунда (настройка `fragment` у самого `freedom` режет только его собственный трафик).
- Опция на сервер (`fragment` в `[[overrides]]`, клавиша `z`), по умолчанию выключена, только для TLS и Reality.

## Этап 7

- Экран правил, генерация правил, валидация, пресеты и подтверждение перезапуска были готовы в 5.2; на этапе 7 добавлено
  недостающее: `ProxyOverride` (см. ниже), `ua-direct`, пометки про QUIC, проверка имён процессов.
- **`ProxyOverride` в PROXY-режиме:** в список обхода системного прокси добавляются простые домены (`domain:x` как
  `x` и `*.x`, `full:x` как `x`) и IPv4-адреса (одиночные и сети /8, /16, /24 как `a.*`) из правил «напрямую» и
  включённых пресетов. Только в режиме `exclude`: в `include` перечисленное должно идти *через* прокси. `keyword:`,
  geosite/geoip и прочие CIDR выразить в списке обхода нельзя, их по-прежнему решает маршрутизация Xray. При изменении
  правил список отправляется повторно (повторное включение прокси не теряет исходные настройки пользователя).
- **`ua-direct`:** в имеющихся `geoip.dat`/`geosite.dat` нет `geoip:ua` и `geosite:category-ua`, поэтому пресет задан
  списком доменов (зона `.ua`, `ukr.net`, `1plus1.video`, `privat24.ua`, `monobank.ua`), по IP не работает; пометка есть
  в названии пресета и в строке подсказки. Если в будущей сборке Xray наборы появятся, их можно вернуть в `presets.toml`.
- **`block-quic`:** по умолчанию выключен (как решено пользователем; в `plan-additions.md` раньше стояло «включён»).
  При `flow=xtls-rprx-vision` UDP/443 уже закрыт ядром: об этом строка `QUIC:` в деталях сервера и первая фраза
  подсказки пресета, когда выбран/подключён такой сервер.
- **Имена процессов Linux:** проверены на машине разработки (Arch): `Discord` (Flatpak: `/app/discord/Discord`),
  `steam`, `steamwebhelper` подтверждены; `vesktop-bin` из Arch запускается через системный Electron (процесс `electron44`),
  имя `vesktop` для него неверно (оставлено для AppImage/Flatpak, помечено в `presets.toml`); `deluge` это Python
  (`python3.x`), помечен как вероятно неверный; остальное не проверено и помечено комментарием.

### Уточнения после этапа 7

## Этап 8
- Статистика: `stats`/`api`/`policy` и dokodemo-инбаунд `api` добавляются в каждый конфиг основного ядра (`api_port = 0`
  выключает; временные ядра пинга его выключают, чтобы не занимать порт). Опрос раз в секунду через
  `xray api statsquery`, показ: скорость и итоги отдельно для VPN и напрямую (`proxy-primary`/`proxy-backup` считаются как VPN).
  Счётчик uplink короткого запроса может прочитаться как 0 (проверено реальным Xray), поэтому тест проверяет downlink.
- Экран настроек: каждая строка = команда `Cmd::Set`, значения проверяет и сохраняет фоновая часть; порты и пути
  применяются при следующем подключении. Включены переключатели `auto_connect` и автозапуска (бэкенды этапа 6).
- Темы: `dark` и `light` (`[ui].theme`).
- Автопинг: `[ping].auto_interval_secs` (60 по умолчанию, 0 = выкл), TCP, без мигания «...»; без открытого интерфейса интервал
  растёт в 5 раз, не более 300 с. Ручной `p` сбрасывает таймер. У значения есть возраст замера («42 ms, 30 с назад», в деталях).
- **Задержка активного сервера:** берётся не из observatory (у Xray нет CLI для `ObservatoryService`, а тянуть gRPC ради
  одной цифры не стали), а из той же проверки соединения через туннель (`generate_204` через socks), на каждом цикле автопинга.

## Пинг: тип замера и устойчивость (после этапа 8)
- Жалоба: пинг прыгал между ~40 и ~200 мс. Причина: один TCP-connect (холодный DNS/ARP, первые пакеты) и URL-замер, в который
  входили запуск временного Xray, TCP до сервера и рукопожатия.
- TCP-пинг: один прогревочный connect (отбрасывается) и 3 замера подряд, показывается медиана (с паузой 80 мс).
- URL-пинг: прогревочный запрос не засчитывается, затем 3 запроса по уже открытому соединению через туннель, медиана.
  Запуск временного ядра и установка соединения до сервера в замер не входят.
- Проверка соединения активного сервера теперь тоже мерит только запрос (часы стартуют после socks-рукопожатия).
- В UI рядом со значением тип замера: в списке `tcp` / `vpn`, в деталях «TCP до сервера» / «через туннель» плюс возраст замера.
  Автопинг и `p` дают `tcp`; URL-режим и задержка активного сервера дают `vpn`.

## Ассеты TUN-копии ядра (Linux)
- Ядро всегда запускается с явным `XRAY_LOCATION_ASSET` (`process::asset_dir`: рядом с бинарником, а для симлинка рядом с реальным
  файлом); это относится и к проверке `run -test`, и к запуску, и к временным ядрам.
- Перед запуском TUN проверяется, что рядом с копией ядра лежат `geoip.dat` и `geosite.dat` (иначе блокирующая проблема с командами установки).
  elf-gate сам их не копирует (sudo не вызывает): это делают `install_commands` и `packaging/scripts/elf-gate-tun.sh`, который
  теперь ставит оба файла и обновляет их, если исходники в `bin/` изменились.
- При старте ядра в журнал пишется строка с путём к xray и к ассетам (и есть ли файлы); та же строка добавляется к ошибке
  «Xray отверг итоговый конфиг». Сообщение «ядро Xray не найдено» теперь перечисляет, где искали.

### Дочерний xray не видит geoip.dat (Linux, TUN)
- В коде elf-gate нет `unshare`, `chroot`, namespace, seccomp, `env_clear`, `systemd-run`/`bwrap`: у ядра та же ФС, что у родителя
  (проверено чтением кода: единственный `pre_exec` ставит `PDEATHSIG`). Причина на стороне окружения/способа запуска не найдена
  по коду, поэтому добавлены автоповтор и отчёт.
- `validate::check_config`: если отказ «окруженческий» (stat/no such file/permission denied/geoip/geosite), проверка повторяется
  «как из shell» (без `XRAY_LOCATION_ASSET`, cwd = каталог ядра). Если так проходит, ядро дальше запускается тем же способом
  (в журнал пишется предупреждение). Если не проходит, отказ содержит полный вывод xray, вывод повтора и отчёт: argv, cwd,
  PATH/HOME/XDG_RUNTIME_DIR, container/flatpak, что видит родитель (`geoip.dat: N байт` или ошибка), `NoNewPrivs`, `Seccomp`,
  `CapEff/CapBnd`, mount namespace, корень, метка LSM. То же пишется в `elf-gated.log`.
- Такие отказы не кешируются (они ничего не говорят о конфиге).

## TUN на Linux: петля, определение процесса, шум (после жалобы пользователя)
- **Петля к адресу VPN-сервера.** Источник: соединения с `198.18.0.1` (адрес TUN) к IP сервера создаёт сам `elf-gated`: фоновый
  TCP-пинг всех серверов (раз в 60 с) и ручной `p`. Правило «процесс elf-gate -> direct» их не спасало, потому что определение
  процесса не работало («no process found for inode»), и пакеты уходили в `proxy` (VPN внутри VPN). Свои сокеты Xray уже привязаны
  к физическому интерфейсу (`autoOutboundsInterface: auto`) и петли не создают. Исправление не зависит от определения процесса:
  в TUN-конфиг добавлены правила `ip -> direct` для адресов ВСЕХ серверов списка (резолвятся до подъёма туннеля) и `domain full: -> direct`
  для их имён и хостов подписок, выше пользовательских правил. `sockopt.mark` + `ip rule` не взяты: правила маршрутизации ядра требуют
  прав, которых у копии ядра (только `cap_net_admin`) нет, а elf-gate sudo не вызывает. Для Windows те же правила работают (одна и та же
  генерация конфига; `autoOutboundsInterface` тоже включён).
- **«no process found for inode 0 / N».** Устранение петли не лечит определение процесса: оно связано с правами ядра. Inode 0 бывает у
  сокетов без владельца (например, TIME_WAIT), ненулевые inode с ошибкой - у процессов, чьи `/proc/<pid>/fd` ядро читать не может.
  Для программ другого пользователя и песочниц нужны `cap_sys_ptrace` и `cap_dac_read_search`. **Результат проверки этой гипотезы
  на машине пользователя в задании не приведён (стояла заглушка)**, поэтому права НЕ выдаются по умолчанию: `ELF_GATE_FULL_CAPS=1
  ./elf-gate-tun.sh` и подсказка `setcap ...` включают их добровольно, в README описано, что они дают. Если в правилах есть
  процессы, а у ядра этих прав нет (`getcap`), при подключении один раз показывается предупреждение (не ошибка).
  Соединения с неопределённым процессом Xray пускает по правилу по умолчанию; шум от его сообщений схлопывается (см. ниже).
- **Шум.** Консольный access-лог Xray включён по умолчанию, если `log.access` не задан; теперь `access: "none"`. Настройка
  «Подробный лог ядра (access)» (`[core].verbose_log`, экран настроек) возвращает access-строки и уровень `info`. Повторяющиеся строки ядра
  (по тексту без чисел) показываются один раз, остальные считаются: «… (ещё N раз)» после окна 10 с.
- **Кеш проверок.** Отказы по причине окружения не кешируются, а такие записи старого файла удаляются при загрузке (причина
  прошлой проблемы с `check-cache.json`).

## Подписки: HWID и JSON-конфиги Xray (Remnawave и подобные)
- **HWID.** `x-hwid` = первые 16 hex от `sha256(machine-id)` (Linux `/etc/machine-id`, Windows `MachineGuid`; запасной вариант: случайное
  значение из часов и PID), создаётся один раз, хранится в `[device].hwid` и одинаково уходит во все подписки. Вместе с ним:
  `x-device-os` (Linux/Windows), `x-ver-os` (VERSION_ID / сборка Windows), `x-device-model: elf-gate`. User-Agent по умолчанию для новых
  подписок `v2rayNG/1.10.4` (существующие подписки сохраняют свой). HWID виден на экране настроек с пояснением, что он занимает слот
  подписки. Новая зависимость `sha2` (sha256 для HWID; для ключа кеша проверок по-прежнему обходимся FNV-1a).
- **JSON-подписка** = массив полных конфигов Xray. Запись целиком хранится как «ссылка» `xrayjson:<json>` (так работает кеш подписок и
  `parse_link`), в интерфейс уходит копия без outbounds (там ключи). Тип сервера «готовый конфиг» (`Server.full`).
- **Цепочки.** Один outbound брать нельзя: `proxy` ходит через следующий узел по `streamSettings.sockopt.dialerProxy` (в старых конфигах
  `proxySettings.tag`), а тот через следующий (в вашем случае последним звеном стоит `freedom` с `fragment`). Берутся входной outbound и
  всё, до чего он дотягивается по этим ссылкам, остальное отбрасывается. Входной = последнее «безусловное» правило провайдера
  (`outboundTag`/`balancerTag`), иначе outbound с тегом `proxy`, иначе первый прокси. Если вход это балансировщик: переносятся он,
  его `selector`-outbounds и `observatory`/`burstObservatory`.
- **Что меняется при сборке.** Теги: вход становится `proxy` (балансировщик тоже `proxy`), остальные получают префикс `pv-`, ссылки
  `dialerProxy`, `selector`, `fallbackTag`, `subjectSelector` поправлены. Наши inbounds/api/stats/правила/DNS остаются, провайдерские
  `routing` и `dns` не копируются. Содержимое outbound (gRPC, Reality, fragment и т.д.) не трогается, **с одним исключением**: Xray 26
  удалил `proxySettings` («migrated to streamSettings.sockopt.dialerProxy»), поэтому он переписывается в `dialerProxy` (проверено
  `xray run -test`).
- **TUN.** Имена всех узлов цепочки резолвятся до подъёма туннеля и подставляются как адреса (имя остаётся как serverName, если его не
  было); все они и их IP попадают в список «мимо туннеля». TCP-пинг и защита от петли используют первый узел цепочки (конец цепочки
  dialerProxy: именно туда машина подключается первой). URL-пинг и проверка соединения идут через всю цепочку (временное ядро с
  тем же конфигом).
- **Заглушки и заголовки.** Нулевой UUID, адрес `0.0.0.0`/`::`, порт 0 или 1 в любом формате (ссылка или JSON), а также записи без
  прокси-outbound (разделители) это строки-сообщения (`info_only`): показываются приглушённо, Enter показывает пояснение, ни пинга,
  ни проверок, ни подключения.
- Для готовых конфигов недоступны fp, фрагментация и роли основной/запасной (цепочка переносится как есть).

## Кеш проверок: ключ и срок
- Ключ записи = хеш конфига + отпечаток окружения (путь, размер и mtime xray, размер и mtime `geoip.dat`/`geosite.dat`) + версия
  Xray (весь файл). Любое изменение делает записи недействительными. Отказы живут не дольше суток, принятия без срока.
  Формат файла 2; файл старого формата отбрасывается.

## Права копии ядра по умолчанию (Linux)
- Проверено пользователем: с `cap_net_admin,cap_sys_ptrace,cap_dac_read_search` ошибки «no process found» исчезают полностью. Эти три
  права теперь выдаются по умолчанию (`install_commands`, подсказки, `elf-gate-tun.sh`, README); `ELF_GATE_FULL_CAPS=0` оставляет
  только `cap_net_admin`. При урезанных правах строки «no process found» скрываются, одно предупреждение при подключении остаётся.

## Удаление серверов и подписок (баг)
- **Причина «вернулось после перезапуска».** Удаление сервера из подписки меняло только память демона: конфиг не писался, а список
  подписки при старте читается из `subscriptions.json` (и обновляется с панели), поэтому сервер появлялся снова. Воспроизведено тестом.
  Отдельной причины, по которой нельзя удалить пустую подписку, найти не удалось: на текущем коде (и в тесте для пустой, «все скрыты»,
  «только заглушки» и «ошибка загрузки») удаление работает; если проблема повторится, нужен текст ошибки или состояние экрана.
- **Новая семантика.** Ручной сервер удаляется (как раньше, с записью в `config.toml`). Сервер подписки скрывается: ключ
  `имя|адрес:порт|хеш id` пишется в `[[hidden]]` того же `config.toml`, при обновлении и перезапуске он остаётся скрытым; вернуть:
  `h` на подписке (показывает скрытые серыми), затем `x` на скрытом. Скрытые не пингуются, не проверяются и не попадают в трей.
- **Удаление подписки** работает в любом состоянии и убирает серверы, `[[subscriptions]]`, запись в `subscriptions.json`, `[[hidden]]` и
  `[[overrides]]` этой подписки. Всё делает демон; интерфейс только шлёт `DeleteServer` / `UnhideServer` / `DeleteGroup`.
- Если удаляемый или скрываемый сервер подключён, в подтверждении об этом сказано, и демон сначала отключается (переключение на
  запасной не делается).

## Строка с клавишами (UX)
- Внизу экрана отдельная строка `ui/hints.rs`, которую не перекрывают ни панели, ни диалоги (рисуется последней в своей строке). Она
  строится из той же таблицы `action::BINDINGS`, что обрабатывает клавиши и рисует справку: у биндинга есть `bar` (как писать клавишу),
  `short` (подпись), `prio` (что остаётся в узком окне) и `scopes` (на каких экранах работает). Подписи уточняются по выбранному элементу
  (Enter: подключить / отключить / свернуть / пояснение; x: удалить / скрыть / вернуть / удалить подписку); недоступные клавиши не
  показываются. Всегда в конце `? помощь  q/Q выход`. В диалогах, вводе и фильтре строка показывает их собственные клавиши. Без связи
  с фоновой частью команды не предлагаются.
- Узкое окно: сначала уходят клавиши с большим `prio`, остальное заменяется на `…`; строка не переносится и не длиннее окна.
- Минимальная ширина окна снижена с 80 до 60 колонок (по требованию к снапшоту 60 колонок); меньше окна по-прежнему показывается
  сообщение «Увеличьте окно», и под ним тоже строка с клавишами.
- Тесты: снапшоты (`insta`, `src/ui/snapshots/*hint_tests*`) для 27 экранов и состояний; проверки, что показанные клавиши действительно
  вызывают те же действия по таблице, что подсказки зависят от элемента и что узкая строка не переполняется.

## Режим приватности
- Переключатель: `Ctrl+P` (свободен в таблице биндингов; обычное `p` по-прежнему пинг), строка в настройках, `[ui].privacy_mode` в
  `config.toml` (переживает перезапуск). При включении экран меняется сразу (не ждёт ответа демона). В статусной строке яркий значок
  `PRIVACY` (виден и при отсутствии связи с демоном).
- Один редактор `redact.rs` на всё: два уровня. `Secrets` (всегда, для диска): ссылки и URL целиком (`схема://***`, токены прячутся в пути),
  UUID, ключи (длинные base64url, pbk), длинные hex. `Full` (экран в режиме приватности) добавляет IP и домены и короткие hex-id.
- Единый стиль: IPv4 `*.*.*.*`, IPv6 `*:*:*:*`, домен `***.tld` (остаётся только последняя метка: восстановить нельзя), ссылки/URL
  `схема://***`, ID и ключи `***`, HWID `****************`. **Порты оставлены** (не секрет и нужны для отладки). **SNI скрывается**
  (`***.tld`: он выдаёт «донора» Reality), как и host/authority; path, serviceName и spiderX заменяются на `***`.
- Где добавлено: список и детали сервера (адрес, SNI, spx, path/host/service, причина отказа), логи в панели и на весь экран, строка
  состояния (ошибки и сообщения), все диалоги (ошибки, уведомления, подтверждения, вопросы демона), экран настроек (HWID, значения),
  правила (значение, совпадающее с адресом сервера), справка/подсказки (в них секретов нет), трей (заголовок). Поле ввода ссылки/подписки
  показывает точки одной длины с вводом (вставка работает, в демон уходит настоящая ссылка).
- Не маскируется: имена серверов и подписок, задержки, режим, статус, правила по доменам и процессам (кроме совпадающих с адресом сервера).
- Копирования в буфер в программе нет, поэтому предупреждение «копируется настоящее значение» не понадобилось.
- Маскирование только на уровне отображения: конфиг, IPC и данные не меняются.
- **Файлы логов без секретов независимо от режима:** все строки приложения пишутся в файл через `redact::secrets`. Найдено и исправлено:
  при ошибке загрузки сохранённого сервера в лог попадала вся ссылка (теперь `схема://***`), ошибки загрузки подписки (reqwest) содержали
  URL с токеном (теперь `without_url()`), отчёты проверки xray пропускаются через `secrets`.

## TCP-пинг в TUN и шум «процесс не найден»
- **Пинг в TUN.** Обычный TCP-connect при поднятом туннеле входит в TUN, и его стек сам завершает рукопожатие (2-24 ms до любых
  адресов). `engine::ping::choose_method` единственное место выбора: при поднятом туннеле простой TCP не выбирается никогда. Linux:
  сокет привязывается к физическому интерфейсу (`SO_BINDTODEVICE`, без прав с Linux 5.7; интерфейс = маршрут по умолчанию не
  `[tun].name`, `physical_default_interface`). Если привязка невозможна (старое ядро, Windows, нет физического интерфейса), пинг идёт
  через временное ядро (URL-замер, медленнее) с пометкой в статусе, а не «выдуманным» числом; при отказе привязки значение «-».
  URL-пинг в TUN снова разрешён: адреса всех серверов в правиле `direct`, поэтому временное ядро не петляет. **Windows:** привязка
  (`IP_UNICAST_IF`) не реализована (нужна проверка на Windows), там TUN-пинг всегда через ядро.
- **Шум.** Строки ядра «no process found» / «not found in /proc/net» / «find local process name» не показываются в TUI ни при каких
  правах; вместо них счётчик `process_unresolved` (в деталях подключённого сервера: «не определён процесс: N соединений»), в файл лога
  раз в минуту одна строка с числом. Включённый «Подробный лог ядра» возвращает строки как есть. (Прежнее скрытие только при урезанных
  правах убрано: под нагрузкой строки идут и с полными правами.)
- **HWID** создаётся при сборке движка (до первого снимка состояния), поэтому на экране настроек он виден сразу.

## Строка клавиш: перенос; приватность: целиком и без домашнего каталога
- Клавиши не влезают в строку: раскладываются на 2-3 строки целыми подсказками (область под подсказки растёт, панели уменьшаются).
  `…` только если не помещается и в три строки (уходят наименее важные), и тогда `? помощь  q/Q выход` всегда в конце. Подписи сокращены
  (`Enter подкл.`/`отключ.`, `Ctrl+P прив.`, `s настр.`, `o сорт.`...). На подключённом сервере Enter отключает, `d` из подсказки убран
  (на другом сервере остаются `Enter подкл.` и `d отключ.`). Снапшоты нижних строк на 80, 120 и 150 колонках; на 120 и 150 нет `…` и
  видны все клавиши экрана.
- Приватность: хост маскируется **целиком** (`***`, без зоны: даже `***.app` выдаёт провайдера); IPv4 `*.*.*.*`, IPv6 `*:*:*:*`, порты
  остаются. Домашний каталог (`/home/<user>`, `/Users/<user>`, `C:\Users\<user>`, `/root`) заменяется на `~` во всём тексте на экране
  (лог, детали, настройки, диалоги); в файлах логов пути остаются как есть (там скрываются только секреты). Имена опций вида
  `streamSettings.sockopt.dialerProxy` не считаются доменами (зона должна быть в нижнем регистре), расширения файлов и `*.go` тоже.
- Тесты: типовые строки xray (deprecated-предупреждения, ошибки dial/handshake с адресами, DNS-ошибки с доменом, пути с именем учётной
  записи), снапшоты экрана с цепочкой из JSON-подписки в режиме приватности (ни зоны, ни домашнего каталога).

## Локализация интерфейса (en / ru / uk)
- **Механизм.** Свой маленький модуль `src/i18n.rs` поверх уже подключённого `toml`: `locales/{en,ru,uk}.toml` вшиваются в бинарник
  (`include_str!`), таблицы разворачиваются в `раздел.ключ`. Готовые крейты (fluent, rust-i18n, gettext) тянут макросы, генерацию кода или
  рантайм ICU ради ~460 строк; нам нужны только подстановка `{имя}`, три формы множественного числа и откат на английский.
- **Язык по умолчанию — английский**, не зависит от языка системы. `ui.language` в `config.toml` (`en`/`ru`/`uk`), первая строка экрана
  настроек («Language / Язык / Мова»), Enter переключает en → ru → uk. Значения показаны своими названиями: English, Русский, Українська.
  Переключение применяется сразу: демон ставит язык при `Set(Language)` и при загрузке конфига, интерфейс берёт его из каждого снимка
  состояния, трей получает язык в модели (`TrayModel.lang`) и перерисовывает меню.
- **Что не переводится:** строки ядра xray, технические имена (VLESS, Reality, TUN, PROXY, SOCKS, имена fp), имена серверов, названия клавиш.
- **Файл лога всегда английский.** Сообщения движка идут через `Engine::logt(level, || t!(..))`: на экран — текст на текущем языке, в файл —
  то же замыканием под `with_lang(En)`. Исключение: тексты ошибок, уже собранные в виде `String` (сеть, разбор ссылок, запуск ядра), попадают
  в файл на языке, действовавшем в момент ошибки; сами они переводятся при создании. Это сознательный компромисс: типизированные ошибки
  с отложенным переводом потребовали бы переписать все `Result<_, String>`.
- **Множественное число:** `ключ.one/.few/.many/.other`; en использует one/other, ru/uk — one/few/many (1, 2, 5, 11, 21, 22 проверены тестами).
  Нет ключа в ru/uk — берётся английский; нет нигде — виден сам ключ, без паники.
- **Тесты:** набор ключей en = ru = uk (расхождения выводятся списком), одинаковые `{плейсхолдеры}`, формы множественного числа, снапшоты
  основных экранов на 120 колонках в трёх языках, проверка, что в `src/` нет кириллицы вне `locales/` и тестов. Юнит-тесты по умолчанию идут
  на русском (`cfg!(test)`), чтобы старые проверки русских текстов не менялись; язык потока задаётся `i18n::set` / `with_lang`.
- Руководство пользователя (`docs/`) остаётся только на русском.

## Хоткеи в русской и украинской раскладке; колонка имени
- `action::map_key` сначала ищет клавишу в `BINDINGS` как есть, затем, если это кириллическая буква, берёт QWERTY-клавишу на том же месте
  (`LAYOUT_KEYS`: ru и uk в одной таблице, регистр сохраняется: `Й` это `Q`, `й` это `q`, Ctrl работает так же). Сами привязки не
  дублируются; в таблице раскладок только соответствие клавиш. Тест проходит по всей таблице привязок и нажимает каждую буквенную клавишу
  латиницей, русской и украинской буквой того же места. Поля ввода (ссылка, фильтр, значение настройки) принимают символы как есть.
- `.` на русской раскладке физически стоит на клавише `/`, но привязка `.` -> `/` не добавлена: в латинской раскладке точка открыла бы фильтр.
  Фильтр на ru/uk доступен через `/` (Shift+\).
- Диалог подтверждения отвечает на физические клавиши `y` и `n` в любой раскладке: на ru/uk это `н` и `т` (`Н` и `Т`); смысл букв не
  учитывается (`д` ничего не подтверждает). Раньше `н` означала «нет» и закрывала диалог без действия, из-за чего Q, y на русской раскладке не выходил.
  В списке выбора `j`/`k` работают и как `о`/`л`.
- Колонка имени в списке серверов занимает всё место до колонки задержки (ширина от ширины панели), задержка и вид замера выровнены по
  правому краю, вид замера всегда занимает четыре колонки. Устаревший транспорт отмечен `†` сразу за именем (обрезается имя, не метка);
  пояснение в деталях сервера. Строка подключённого сервера `N tcp · M vpn` прижата к правому краю тем же блоком шириной 16.

## Ядро и поток, который его запустил (F2, Linux)

- Ядро Xray запускается с `PR_SET_PDEATHSIG(SIGKILL)` (`src/platform/linux/child.rs`). Так ядро не переживает
  elf-gate, даже если его убили `kill -9`.
- **Ограничение:** сигнал приходит, когда завершается *поток*, который сделал `fork`, а не процесс. Ядро живёт, пока
  жив запустивший его поток. Сейчас ядро запускается из задач на воркерах tokio, они живут столько же, сколько
  runtime, поэтому всё работает.
- Следствие: запускать ядро из `spawn_blocking` или из отдельного короткоживущего потока нельзя. Потоки пула
  `spawn_blocking` завершаются после простоя (по умолчанию 10 с), и ядро получило бы SIGKILL.
- Решение: оставить PDEATHSIG, ограничение записать здесь и закрепить тестами
  (`child_dies_with_the_thread_that_started_it`, `child_lives_while_its_thread_lives` в `child.rs`). Если тест упадёт,
  семантика PDEATHSIG изменилась, и `prepare` надо пересмотреть.
- Отвергнуто: `debug_assert!` на «текущий поток это воркер tokio»: у потоков `spawn_blocking` то же имя
  (`tokio-runtime-worker`), различить их нечем. Отвергнуто: всегда запускать через `--supervise`: это меняет схему
  запуска и добавляет процесс; супервизор остаётся только для ядра с capability (см. выше).

## Защита named pipe на Windows (F3)

- Имя канала содержит SID пользователя (`\\.\pipe\elf-gate-<SID>`), а не `%USERNAME%`: переменную окружения можно
  подменить. Старое имя не поддерживается.
- Имя предсказуемо, поэтому другой пользователь может создать канал первым. Защита из двух частей:
  1. демон создаёт канал с `FILE_FLAG_FIRST_PIPE_INSTANCE` и дескриптором `O:<SID>D:P(A;;GA;;;<SID>)(A;;GA;;;SY)S:(ML;;NW;;;ME)`:
     владелец это пользователь, доступ только у него и у SYSTEM;
  2. клиент после подключения читает **владельца объекта канала** (`GetSecurityInfo`, `SE_KERNEL_OBJECT`,
     `OWNER_SECURITY_INFORMATION`) и отказывается, если это не его SID.
- Метка целостности «средний, без записи вверх» (`S:(ML;;NW;;;ME)`) нужна, чтобы неповышенный клиент мог писать в канал
  повышенного демона: без неё канал получил бы высокий уровень, и запись из среднего уровня была бы запрещена.
- Отвергнуто: проверять токен процесса-сервера (`GetNamedPipeServerProcessId`, `OpenProcessToken`). Неповышенный клиент
  не обязан мочь открыть токен повышенного `elf-gated.exe`, а повышенный фон нужен для TUN (перезапуск через UAC).
  Владельца канала создатель задаёт сам в дескрипторе (SID пользователя разрешён любому процессу этого пользователя), так
  что повышенный демон проходит проверку, а чужой пользователь указать чужой SID владельцем не может.
- Проверено только компиляцией под `x86_64-pc-windows-gnu`; сценарии в `docs/windows-checklist.md`.

## Мягкая остановка Xray на Windows (v1.0.3)

- **Причина сбоя.** `ChildGuard::terminate` на Windows делал `start_kill` (TerminateProcess). Убитый так Xray не успевал
  закрыть TUN-адаптер wintun, и следующий запуск ядра в TUN падал: `Cannot create a file when that file already
  exists` (0xC0000035 / 0xB7). Первое подключение после перезагрузки работало, потому что адаптера ещё не было.
- **Решение.** Ядро запускается с `CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP`. Остановка: `CTRL_BREAK_EVENT`, ожидание
  до 5 с (`STOP_TIMEOUT_WINDOWS`), и только потом TerminateProcess. Go-рантайм воспринимает CTRL_BREAK как
  `os.Interrupt`, Xray закрывает inbound'ы, включая TUN.
- **Почему не просто `GenerateConsoleCtrlEvent`.** Событие доходит только до процессов, которые делят консоль с
  вызывающим. Фоновый `elf-gated.exe` запущен как `DETACHED_PROCESS` (консоли нет), а у ядра с `CREATE_NO_WINDOW` своя
  скрытая консоль. Поэтому перед отправкой фон делает `FreeConsole` и `AttachConsole(pid ядра)`, отправляет
  `CTRL_BREAK_EVENT` группе ядра (id группы равен pid ядра, сам фон в эту группу не входит и событие не получает)
  и снова `FreeConsole`. Вызовы идут под мьютексом: процесс может быть подключён только к одной консоли.
- Если `AttachConsole` или отправка не удались, остаётся прежний путь: TerminateProcess (запись в журнал).
- Linux не менялся: SIGTERM и 3 с (6 с под супервизором).
- Отвергнуто: отдельный вспомогательный процесс-«остановщик» (лишний бинарник); остановка через API Xray (его gRPC
  не отключаем и не имеет команды остановки).
- Проверено только компиляцией под `x86_64-pc-windows-gnu`; сценарии в `docs/windows-checklist.md`.

## Адаптер TUN перед запуском ядра (v1.0.3)

- Каждый запуск ядра идёт через `start_after_stop` (`src/engine/session.rs`): остановка старого ядра, затем ожидание,
  пока адаптер с нашим именем исчезнет (опрос `interface_exists` до 5 с), затем удаление того, что осталось
  (`TunHost::remove_stale_adapter`), затем запуск. Первое подключение, переподключение, смена правил и смена сервера
  проходят этот путь без обходных.
- Удаление (`src/platform/windows/adapter.rs`): SetupAPI, класс Net, без `DIGCF_PRESENT`, то есть вместе с «призраками»
  (устройство есть в реестре, но не подключено). Удаляется устройство, только если его hardware id содержит `wintun` И
  имя соединения (`...\Network\{4D36E972-...}\<NetCfgInstanceId>\Connection\Name`) равно имени из конфига. Чужие
  адаптеры, в том числе другие Wintun, не трогаются. Нужны права администратора, они у TUN уже есть.
- Отвергнуто: `pnputil /remove-device`: список устройств приходит локализованным текстом, и сопоставить имя
  соединения с экземпляром устройства через него нельзя.
- На Linux ничего не ждётся и не удаляется (`adapter_lifecycle_managed` по умолчанию false): адаптер исчезает вместе с
  ядром.
- Проверено только компиляцией под `x86_64-pc-windows-gnu`; порядок «остановка, ожидание, запуск» покрыт тестами с моком.

## Предупреждения входящих о закрытых соединениях (P9)

- Строки Xray `proxy/http` и `proxy/socks` с «closed pipe» или «unexpected EOF» (программа сама закрыла соединение)
  в интерфейсе видны только при уровне журнала ядра `debug`; ошибки `app/dns` и остальные остаются.
- Скрытые строки пишутся в файл журнала как есть (цель `core`), но адреса и имена проходят через
  `redact::text(.., Full)`: что журнал говорит о посещаемых сайтах, приватно. Решение принято без вопроса.
- Скрытые строки не считаются в счётчике «процесс не определён» и не попадают в свёрнутые повторы.

## Мышь (части A, B, C)

- Карта областей `ui::hits::HitMap` лежит в `AppState` (внутри `RefCell`: экраны рисуются из `&AppState`) и пересобирается
  каждый кадр. Клик берёт самую верхнюю область; окно регистрирует блокирующую область на весь экран и на себя, поэтому
  клик и колесо вне окна не доходят до того, что под ним. Строка клавиш рисуется последней и остаётся кликабельной.
- Клик превращается в то же, что делает клавиша: `Target::Key` (нажатие клавиши, подсказки и кнопки окон),
  `Target::Action` (то же, что клавиша действия), выбор строки и «Enter на выбранной строке». Своей логики у мыши нет.
- Двойной клик: две нажатия на один и тот же элемент не позже чем через 400 мс. Клик по уже выбранной строке (в той же
  панели) тоже делает Enter, как просили.
- Колесо в списках с выделением двигает выделение на 3 строки: окно следует за выделением (`ui::scroll`), отдельного
  смещения у такого списка нет. Журнал и справка прокручиваются как текст; прокрутка журнала вверх отключает
  автопрокрутку (то же `scroll_logs`, что и у клавиш).
- Клик по чекбоксу правила - выбор строки и `Space`. Клик по самой строке правила только выбирает.
- Строки «обновить» и «удалить» на экране подписки срабатывают с одного клика (выбор и Enter; удаление всё равно
  спрашивает). Сброс значения на экране подписки - клавиша `r` в строке клавиш, она кликабельна.
- Окна с вопросом и ошибкой получили настоящие кнопки (клавиша-«кеп» и подпись) вместо текста подсказки: `y/Enter да`,
  `n/Esc нет`, `Esc закрыть`, `c проверка`. Остальные окна (ввод, выбор, процессы, обновление) работают через строку клавиш.
- Не сделано: «клик в поле ввода ставит курсор в позицию клика». У поля ввода нет курсора внутри строки (текст только
  дописывается и стирается с конца), позиционировать нечего. Вводить курсор ради этого - отдельная задача.
- Вид клавиш: «кеп» из пробела, клавиши и пробела на фоне surface0 (в теме terminal и при NO_COLOR - инверсия), подпись
  сразу за ним, один пробел между подсказками. Ширина подсказки та же, что была (клавиша, пробел, подпись, два пробела),
  поэтому строка клавиш не стала длиннее на 80 колонках, и сокращать подписи не пришлось.
- Подсветка под курсором: подсказка и кнопка - цвет акцента (инверсия с подчёркиванием в terminal/NO_COLOR), строка
  списка - фон выделения (подчёркивание в terminal/NO_COLOR). Подсвечивается верхний кликабельный элемент, панель целиком
  не подсвечивается. Кадр рисуется заново, только когда элемент под курсором сменился.
- Настройка «Мышь» выключена: события не обрабатываются, захват мыши терминалу возвращается, вид клавиш остаётся.
- Терминал без событий мыши (старый conhost): включение захвата не падает при ошибке, события просто не приходят.

## Правила без перезапуска ядра (часть D)

- **Что есть в Xray 26.11.9 (D0).** `RoutingService` содержит `AddRule` (с `shouldAppend`), `RemoveRule` (по `ruleTag`),
  `ListRule`, `TestRoute`, `GetBalancerInfo`, `OverrideBalancerTarget`. В CLI это `xray api adrules`, `rmrules`, `lsrules`.
  Раньше в `api.services` был только `StatsService`; добавлен `RoutingService`.
- **Как применяем.** `adrules` без `-append` заменяет весь список правил одним вызовом, поэтому порядок после изменения
  в точности как при полном запуске с новым конфигом: мы строим новый конфиг тем же `build_with` и отправляем его
  `routing.rules` целиком. Это проверено на настоящем Xray (`lsrules` до и после; интеграционный тест). Удалять и добавлять
  правила по одному тегу не нужно и опаснее: между вызовами список был бы неполным.
- **ruleTag.** Правила Xray у нас склеены по категориям (все домены пресетов и правил пользователя - одно правило
  `domain`), поэтому тег стоит на категории, а не на каждом пресете: `elf-api`, `elf-health`, `elf-servers-ip`,
  `elf-servers-domain`, `elf-self`, `elf-block-udp443`, `elf-always-direct`, `elf-processes`, `elf-domains`, `elf-ips`,
  `elf-rest-direct`, `elf-rest-proxy`, `elf-dns-hijack`, `elf-dns-tunnel`, `elf-dns-local`. Теги стабильные.
- **Что идёт через API, что перезапускает.** Новый конфиг сравнивается с тем, с которым ядро запущено: если без
  `routing.rules` они равны (входящие, исходящие, DNS, балансировщики, наблюдатель), правила уходят через API. Иначе
  вопрос о перезапуске, как раньше. Смена режима include/exclude всегда перезапускает (меняет DNS и последнее правило);
  смена сервера, DNS, портов, настроек TUN и смешанного режима идёт через подключение, то есть тоже с перезапуском.
- **Пресеты, которым нужен перезапуск (D5).** В режиме PROXY через API идут все. В режиме TUN перезапуск нужен
  `games-direct`, `ru-direct`, `ua-direct`: они перечисляют домены, а домены меняют секцию DNS (какие имена разрешать
  через туннель, какие локально). Через API идут `discord-only`, `torrents-direct`, `local-direct`, `block-quic`, правила
  по IP и по процессам, а правила по доменам в TUN перезапускают. Таблица закреплена тестом
  `the_presets_that_still_need_a_restart_are_the_ones_that_touch_the_dns`.
- **Ошибка API** - запись в журнал и перезапуск тем же путём, что первое подключение. Изменения, пришедшие, пока вызов
  идёт, отправляются следующим вызовом с правилами на тот момент (вызовы не обгоняют друг друга).
- `run/xray.json` обновляется после успешного вызова. Системный прокси получает новый список обхода.
- После API в статусе: «Правила применены без переподключения». Подсказка про перезапуск программ (старые соединения
  держат старый маршрут) показывается только при перезапуске ядра. Установленные соединения при смене правил не рвутся
  (проверено: соединение, открытое до вызова, получает ответ после; новые соединения идут по новым правилам).

## Правила по процессам и длинные имена на Linux (часть E)

- **По какому имени сопоставляет Xray.** Проверено на установленном Xray 26.11.9 (копия `curl` под именем
  `chrome_crashpad_handler` ходит через socks-вход; интеграционный тест
  `a_process_rule_matches_a_program_with_a_name_longer_than_15_characters`): правило `process: ["chrome_crashpad_handler"]`
  срабатывает, правило с первыми 15 символами (`chrome_crashpad`, то есть тем, что ядро отдаёт в `comm`) - нет. Значит Xray
  сравнивает с именем файла `/proc/<pid>/exe`, а не с `comm`. То же для `cowork-linux-helper`.
- **Решение.** Правило сохраняется с полным именем как есть (`validate` не режет и не меняет регистр, только убирает
  `.exe`); полное и обрезанное имя вместе или путь не нужны. Тест по JSON: имя в `routing.rules` не обрезано.
- **Выбор процесса** (`TunHost::running_processes`) уже показывал basename `/proc/<pid>/exe`, а не `comm`; теперь это
  покрыто тестом на подставном `/proc` (`processes_in`): длинные имена целиком, дубликаты склеены, `(deleted)` убран.
- Не проверялось: программы других пользователей и в песочнице без `cap_sys_ptrace`/`cap_dac_read_search` (тогда `exe`
  недоступен и ядро пишет «no process found» - это уже описано в части про права ядра).

## Адрес API ядра (после части D)

- **Угроза.** `RoutingService` меняет маршрутизацию всей машины, а `StatsService` читает счётчики; открытый фиксированный
  порт `127.0.0.1:10085` позволял любому локальному процессу (другому пользователю тоже) переписать правила.
- **Проверено на Xray 26.11.9.** Вход api типа `dokodemo-door` принимает в `listen` путь к unix-сокету; суффикс `,0600`
  задаёт права файла сокета (файл получился `srw-------`), а `xray api ... --server=unix:///путь` работает для
  `statsquery`, `lsrules` и `adrules`. Без суффикса права были 0755. Тест с настоящим ядром:
  `the_api_listens_on_a_socket_only_the_owner_can_open`.
- **Решение.** Адрес выбирается при каждом запуске ядра (`xray::api_endpoint::ApiEndpoint::choose`): на Linux сокет
  `run/api.sock` в каталоге состояния (он создаётся с правами 0700, сам сокет 0600; старый файл удаляется перед запуском);
  на Windows и если путь длиннее 100 байт (предел `sun_path` 108) - случайный свободный порт на `127.0.0.1`, каждый раз
  новый, никогда не 10085. Адрес живёт только в памяти (`CoreConfig::api_endpoint`, не сохраняется) и берётся оттуда
  статистикой и применением правил.
- **Настройка «Порт API» убрана** из экрана настроек (порт больше не задаётся). В `config.toml` выключатель -
  `core.api_enabled` (bool, по умолчанию `true`; `false` выключает статистику и применение правил без перезапуска).
  Старый `core.api_port` читается один раз (миграция схемы 2): `0` даёт `api_enabled = false`, любой другой порт -
  `true`; файл переписывается с `schema = 2`, и `api_port` больше не пишется. Тест
  `the_old_api_port_becomes_api_enabled_and_is_not_written_again`.
- **Остаточный риск.** Порт на Windows виден любому локальному процессу, пока работает ядро: Xray не умеет api-вход на
  именованном канале. Порт случайный и меняется при каждом запуске, но это защита от случайного, а не от целенаправленного
  локального процесса. Unix-сокеты есть в Windows 10+, но Xray на Windows их для этого входа не проверялся.
