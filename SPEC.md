# ТЗ: elf-gate - TUI-клиент для Xray под Windows и Linux

Кодовое название `elf-gate`: крейт `elf-gate`, бинарник `elf-gate` / `elf-gate.exe`.

## 1. Цель

Консольный (TUI) клиент для Windows и Linux на Rust, который управляет готовым ядром Xray-core: импортирует серверы из ссылок и подписок, генерирует конфиг, запускает ядро, направляет в него трафик (системный прокси или TUN), показывает логи, пинг и статистику, позволяет гибко решать, что идёт через VPN, а что напрямую - по сайтам, IP и процессам.

Основной сценарий использования: пользователи из России, которым через VPN нужен в первую очередь Discord (включая голос и стримы, а они идут по UDP), а игры, лаунчеры, торренты и российские сайты должны идти напрямую. Клиент должен уметь заменить для них ExitLag и подобные программы. Поэтому режим TUN с правилами по процессам - ключевая функция, а не дополнительная.

Ядро Xray не пишется и не модифицируется - используется готовый бинарник `xray` (`xray.exe` на Windows) как дочерний процесс.

### Не входит в проект
- Серверная часть, панели, развёртывание VPS.
- GUI, Android, iOS, macOS.
- Собственные протоколы и любая модификация Xray.
- Автоскачивание `xray` и других бинарников в первых этапах (пользователь кладёт их сам).

## 2. Платформы и разработка

- Поддерживаемые платформы: Windows 10/11 x64 (основная для пользователей) и Linux x64 (основная для разработки; целевые окружения - systemd-дистрибутивы, GNOME и KDE).
- Разработка ведётся на Linux. Код с самого начала кроссплатформенный: всё платформенное - только в модуле `platform` за трейтами, остальной код от ОС не зависит. `#[cfg(...)]` вне `platform` не допускается (кроме выбора путей к бинарникам вида `xray` / `xray.exe`).
- Сборка под Windows с Linux: `cargo build --target x86_64-pc-windows-gnu` (нужен `mingw-w64`) для быстрой проверки компиляции; релизные Windows-сборки и тесты - в CI на `windows-latest`.
- CI (GitHub Actions): матрица `ubuntu-latest` + `windows-latest`, шаги `fmt --check`, `clippy -D warnings`, `test`, `build --release`; артефакты релизных сборок для обеих ОС. Настраивается на этапе 1.
- Критерии готовности помечены `[Linux]`, `[Windows]` или без пометки (обе ОС). Пункты `[Windows]`, которые нельзя проверить без Windows-машины, допускается закрыть позже (виртуальная машина или реальный ПК), но код и CI для них обязательны в своём этапе. Непроверенные пункты фиксировать в `docs/windows-checklist.md`.

## 3. Стек

- Rust stable, edition 2021, один бинарный крейт.
- UI: `ratatui` + `crossterm`.
- Асинхронность: `tokio` (rt-multi-thread, process, time, sync, net, signal).
- Сеть: `reqwest` (rustls, без native-tls).
- Парсинг: `url`, `base64`, `percent-encoding`.
- Сериализация: `serde`, `serde_json`, `toml`.
- Windows (`[target.'cfg(windows)'.dependencies]`): крейт `windows` (реестр, `InternetSetOptionW`, Job Objects, `ShellExecuteW` для повышения прав, `SetConsoleCtrlHandler`).
- Linux (`[target.'cfg(unix)'.dependencies]`): `nix` (сигналы, `prctl(PR_SET_PDEATHSIG)`, проверка euid).
- Ошибки: `thiserror` в модулях, `anyhow` на верхнем уровне.
- Логи приложения: `tracing` + `tracing-appender` в файл (stdout занят TUI, в терминал ничего не печатать).
- Пути: `directories`.
- Тесты: стандартные + `insta` для snapshot-тестов генерации конфига.

## 4. Общие требования

- UI никогда не паникует и не блокируется: все долгие операции (сеть, процессы, пинг) идут в фоновых задачах tokio и сообщают результат через канал событий.
- Любая ошибка показывается пользователю (строка статуса или всплывающее окно), подробности пишутся в лог-файл.
- Panic hook обязан: восстановить терминал (выйти из raw mode / alternate screen), выключить системный прокси, если его включали мы, остановить ядро и TUN, записать панику в лог.
- `unsafe` - только в обёртках над API ОС внутри `platform`, каждый блок с комментарием.
- `cargo clippy -- -D warnings` и `cargo fmt --check` проходят на каждом этапе.
- Git: коммиты от имени `z3nghoul <99019933+z3nghoul@users.noreply.github.com>` (настроить `git config user.name/user.email` в репозитории), один логический шаг - один коммит, сообщения на английском в повелительном наклонении.

### Хранение данных

Пути через крейт `directories`: Windows - `%APPDATA%\elf-gate\`, Linux - `~/.config/elf-gate/` (конфиг) и `~/.local/state/elf-gate/` (state, логи, run).

- `config.toml` - настройки, подписки, ручные серверы, правила.
- `state.json` - служебное состояние: включали ли мы прокси, прежние значения прокси, PID ядра, был ли поднят TUN.
- `logs/elf-gate.log` - лог приложения (ротация по дням, хранить 7 файлов).
- `run/` - сгенерированные конфиги ядра (перезаписываются при каждом подключении).

Пример ниже - для Windows; на Linux `xray_path` вида `/usr/local/bin/xray`.

Пример `config.toml`:

```toml
[core]
xray_path = "C:\\tools\\xray\\xray.exe"   # рядом должны лежать geoip.dat и geosite.dat
socks_port = 10808
http_port = 10809
api_port = 10085
log_level = "warning"

[mode]
traffic = "proxy"       # proxy | tun
routing = "exclude"     # exclude - всё через VPN, кроме правил; include - только правила через VPN

[proxy]
set_system_proxy = true
bypass = ["localhost", "127.*", "10.*", "172.16.*", "192.168.*", "<local>"]

[ping]
mode = "tcp"            # tcp | url
url = "https://www.gstatic.com/generate_204"
timeout_ms = 3000

[[subscriptions]]
name = "main"
url = "https://example.com/sub/xxxx"
user_agent = "v2rayN/7.0"
auto_update_hours = 12

[[servers]]             # серверы, добавленные вручную
link = "vless://..."

[[rules]]
kind = "domain"         # domain | ip | geosite | geoip | process
value = "example.com"
match = "suffix"        # для domain: suffix | full | keyword

[presets]

```

## 6. Этапы

Каждый этап заканчивается рабочим состоянием, коммитом и проверкой критериев готовности. К следующему этапу не переходить, пока не выполнены критерии текущего.

### Этап 1. Каркас TUI (на моковых данных)

Цель: полностью навигируемый интерфейс без реальной сети и ядра.

Раскладка главного экрана:

```
+ Серверы ---------------+ Детали -----------------+
| > DE-1      42 ms      | Протокол: VLESS+Reality |
|   NL-2      58 ms      | Адрес:    host:443      |
|   FI-1    timeout      | SNI:      ...           |
+------------------------+-------------------------+
| Логи                                             |
| 02:25:23 accepted //discord.com:443 [proxy]      |
+--------------------------------------------------+
| o Отключено | PROXY | up 0 B  down 0 B | ? помощь|
+--------------------------------------------------+
```

Требования:
- Главный цикл: `crossterm` EventStream + тик 250 мс + канал фоновых событий, всё через `tokio::select!`.
- Панели: серверы (сгруппированы по подпискам, группы сворачиваются), детали, логи, строка статуса (состояние, режим PROXY/TUN, трафик).
- Фокус переключается `Tab` / `Shift+Tab`, активная панель выделена рамкой.
- Экраны-заглушки: правила, настройки, справка.
- Всплывающие окна: ввод текста (для ссылки), подтверждение (да/нет), ошибка.
- Фильтр списка серверов по `/` (подстрока в имени).
- Логи: кольцевой буфер на 2000 строк, прокрутка, режим «на весь экран», автопрокрутка вниз, пока пользователь не прокрутил вверх.
- Корректная перерисовка при изменении размера окна, минимальный размер 80x24 (меньше - сообщение «увеличьте окно»).
- Тема в `theme.rs`, без хардкода цветов в виджетах.
- Моковые данные: 2 подписки по 3-5 серверов, генератор фейковых логов раз в секунду.
- Panic hook и восстановление терминала уже на этом этапе.
- Каркас модуля `platform` с трейтами и пустыми/моковыми реализациями для обеих ОС; CI с матрицей Linux + Windows.

Горячие клавиши:

| Клавиша | Действие |
|---|---|
| `q` / `Ctrl+C` | выход (с подтверждением, если подключено) |
| `j` `k` / стрелки | перемещение по списку |
| `Enter` | подключиться к выбранному серверу |
| `d` | отключиться |
| `t` | переключить режим PROXY / TUN |
| `p` | пинг всех серверов |
| `o` | сортировка по пингу |
| `u` | обновить подписки |
| `a` | добавить сервер или подписку по ссылке |
| `x` | удалить выбранное (с подтверждением) |
| `r` | экран правил |
| `s` | экран настроек |
| `l` | логи на весь экран |
| `/` | фильтр |
| `?` | справка |
| `Esc` | закрыть окно / вернуться |

Критерии готовности:
- Все клавиши из таблицы работают на моках (подключение и смена режима имитируются сменой статуса).
- Изменение размера окна не ломает раскладку.
- Искусственная паника (скрытая отладочная клавиша, только в debug-сборке) возвращает терминал в нормальное состояние.
- CI зелёный на обеих ОС, `cargo build --target x86_64-pc-windows-gnu` проходит локально на Linux.

### Этап 2. Модель данных, парсинг ссылок, генерация конфига

- Структура `Server`: имя, адрес, порт, uuid, flow, security (`none` | `tls` | `reality`), transport (`tcp` | `xhttp` | `grpc` | `ws`), параметры TLS/Reality (sni, fp, alpn, pbk, sid, spx, allowInsecure), параметры транспорта (path, host, mode, serviceName), исходная ссылка.
- Парсер `vless://uuid@host:port?params#name` со всеми параметрами выше; имя из фрагмента декодируется из percent-encoding.
- Неизвестные схемы (`vmess://`, `trojan://`, `ss://`, `hysteria2://`) не роняют импорт: сервер помечается как неподдерживаемый и показывается серым. Поддержку добавить позже отдельной задачей.
- Генератор конфига Xray:
  - `log.loglevel` из настроек;
  - inbounds: `socks` на `127.0.0.1:socks_port` (с включённым UDP) и `http` на `127.0.0.1:http_port`, sniffing включён (`http`, `tls`, `quic`) - без него не будут работать правила по доменам;
  - outbounds: `proxy` (выбранный сервер), `direct` (freedom), `block` (blackhole);
  - routing: `domainStrategy = IPIfNonMatch`, правило `geoip:private -> direct`, место под пользовательские правила (этап 7);
  - stats/api-секции пока не добавлять (этап 8).
- Экран деталей показывает реальные поля сервера.

Критерии готовности:
- Юнит-тесты парсера: минимум 10 фикстур (Reality+tcp+vision, Reality+xhttp, TLS+ws, TLS+grpc, кириллица и эмодзи в имени, IPv6-адрес в квадратных скобках, отсутствующие необязательные параметры, битая ссылка -> ошибка, а не паника).
- Snapshot-тесты (`insta`) генерации конфига для каждого типа транспорта.
- Ручная вставка ссылки через `a` добавляет сервер в список и сохраняет в `config.toml`.

### Этап 3. Управление ядром

- Запуск `xray run -c <run/xray.json>` через `tokio::process::Command`; на Windows без окна консоли (`CREATE_NO_WINDOW`).
- Перед запуском: проверить, что `xray_path` существует и порты свободны; иначе - понятная ошибка в UI.
- stdout и stderr ядра построчно идут в панель логов (с меткой источника), уровни `[Warning]`/`[Error]` подсвечиваются.
- Дочерние процессы должны умирать вместе с приложением даже при его аварийном завершении (трейт `ChildGuard`): Windows - Job Object с `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, Linux - `prctl(PR_SET_PDEATHSIG, SIGKILL)` в `pre_exec`. Касается всех дочерних процессов: ядро, временные ядра для пинга, TUN-бэкенд.
- Отключение: корректное завершение процесса, ожидание до 3 с, затем принудительное.
- Если ядро упало само - статус «Ошибка», последние строки stderr во всплывающем окне, без автоперезапуска.
- Переключение сервера при активном подключении = остановка + запуск с новым конфигом.

Критерии готовности:
- С реальным рабочим сервером: `curl -x socks5h://127.0.0.1:10808 https://ifconfig.me` показывает IP сервера.
- [Windows] После закрытия окна терминала крестиком в диспетчере задач не остаётся `xray.exe`.
- [Linux] После `kill -9` процесса `elf-gate` не остаётся процесса `xray` (`pgrep xray`).
- Невалидный путь к ядру и занятый порт дают понятные сообщения.

### Этап 4. Системный прокси

- Трейт `SystemProxy { enable(addr, bypass), disable(), current(), is_supported() }`, реализации для Windows и Linux, мок для тестов.
- Linux: GNOME - `gsettings` (`org.gnome.system.proxy`, режим `manual`, http/https/socks, `ignore-hosts`); KDE - `kwriteconfig5`/`kwriteconfig6` в `kioslaverc` + уведомление через `dbus-send`. Окружение определяется по `XDG_CURRENT_DESKTOP`. Прежние значения сохраняются в `state.json` так же, как на Windows. Если окружение не поддерживается - системный прокси не трогается, в UI подсказка с адресами `127.0.0.1:<port>` для ручной настройки и рекомендация режима TUN.
- Windows, включение: сохранить текущие `ProxyEnable`, `ProxyServer`, `ProxyOverride` из `HKCU\Software\Microsoft\Windows\CurrentVersion\Internet Settings` в `state.json`, записать новые значения, затем вызвать `InternetSetOptionW` с `INTERNET_OPTION_SETTINGS_CHANGED` и `INTERNET_OPTION_REFRESH`.
- Выключение: восстановить сохранённые значения и снова уведомить систему.
- Восстановление после сбоя: при старте, если `state.json` говорит, что прокси включали мы, а ядро не запущено, - восстановить прежние настройки и сообщить об этом в логах.
- Выключение прокси вызывается из: обычного выхода, `Ctrl+C`, panic hook, обработчика завершения (трейт `ShutdownSignals`: Windows - `SetConsoleCtrlHandler` с `CTRL_CLOSE_EVENT`, `CTRL_LOGOFF_EVENT`, `CTRL_SHUTDOWN_EVENT`; Linux - `SIGTERM`, `SIGHUP`).
- Настройка `set_system_proxy = false` - режим, в котором прокси не трогается (для ручной настройки программ).

Критерии готовности:
- После подключения браузер без своих настроек прокси (Windows - Edge/Chrome, Linux - Chrome/Firefox с «системными настройками») ходит через сервер. [Linux] проверить на GNOME и KDE.
- Убийство процесса `elf-gate` (диспетчер задач / `kill -9`), затем повторный запуск - прокси возвращается к исходному состоянию.
- Если до запуска у пользователя был свой прокси, после выхода он восстановлен как был.

### Этап 5. Режим TUN и правила по процессам

Ключевой этап: без него клиент не работает для Discord (голос и стримы идут по UDP и игнорируют системный прокси).

#### 5.1. Исследование (до написания кода)

Результаты записать в `docs/tun-research.md` и согласовать выбор с владельцем проекта:
1. Есть ли в актуальной версии Xray-core TUN-инбаунд на Windows и Linux, как он настраивается, какие нужны файлы (на Windows - `wintun.dll`).
2. Есть ли в Xray правило маршрутизации по имени процесса и работает ли оно на обеих ОС.
3. Если чего-то нет - вариант с sing-box в роли TUN-слоя перед Xray: sing-box поднимает tun-инбаунд, применяет правила `process_name`, трафик для VPN отправляет в socks-инбаунд Xray (с UDP), остальное - напрямую. Учесть, что sing-box не поддерживает XHTTP, поэтому полностью заменять им Xray нельзя. Выбранный вариант должен работать одинаково на Windows и Linux.
4. Передача UDP через VLESS (Xray, xudp): работает ли голос и демонстрация экрана Discord, какие задержки.
5. Требования окружения: права администратора (Windows) и root или `CAP_NET_ADMIN` (Linux), DNS внутри TUN (на Linux - взаимодействие с `systemd-resolved`) (без утечек и без поломки прямых российских сайтов), защита от петли маршрутизации (трафик до самого VPN-сервера и до процесса ядра - всегда напрямую), поведение при сне/смене сети.

#### 5.2. Реализация

- Переключатель режима PROXY / TUN (клавиша `t`, настройки, строка статуса). В режиме TUN системный прокси не включается.
- Права (трейт `Privileges`): Windows - при выборе TUN без прав диалог «перезапустить с правами администратора?», перезапуск через `ShellExecuteW` с `runas` и флагом командной строки, который сразу подключает в TUN. Linux - если нет root/`CAP_NET_ADMIN`, понятное сообщение с командами (`sudo elf-gate --tun` или однократный `setcap cap_net_admin+ep` на бинарник TUN-бэкенда); при запуске через sudo конфиг и state берутся из домашней папки исходного пользователя (`SUDO_USER`).
- Проверка окружения перед стартом: наличие выбранного TUN-бэкенда, на Windows - `wintun.dll`, на Linux - `/dev/net/tun`; понятная ошибка, если чего-то нет.
- Два режима маршрутизации (`[mode].routing`):
  - `exclude` - через VPN идёт всё, кроме правил (процессы, домены, IP напрямую);
  - `include` - через VPN идут только процессы и домены из правил, всё остальное напрямую. Это режим «как ExitLag».
- Тип правила `process` (имя исполняемого файла: на Windows без учёта регистра, например `Discord.exe`; на Linux - точное имя, например `Discord`). Пресеты содержат имена для обеих ОС. В режиме PROXY правила по процессам показываются неактивными с пояснением «работает только в режиме TUN».
- Выход, падение, panic hook и закрытие консоли полностью убирают TUN-интерфейс и маршруты; при старте - проверка и очистка остатков по `state.json`.

Критерии готовности:
- Режим TUN, `include` + `Discord.exe`: голосовой звонок и просмотр демонстрации экрана в Discord работают через сервер; браузер при этом ходит со своего IP.
- Режим TUN, `exclude` + `steam.exe`: загрузка в Steam не увеличивает трафик через сервер (проверка по логам ядра, а после этапа 8 - по статистике).
- Программа, игнорирующая системный прокси, в режиме TUN (`exclude`, без правил) ходит через сервер.
- После выхода и после аварийного убийства процесса в системе не остаётся TUN-интерфейса, интернет работает (Windows - диспетчер задач, Linux - `kill -9` и проверка `ip link`, `ip route`, `resolvectl`).

### Этап 6. Подписки, сохранение, пинг

- Загрузка подписки через `reqwest` с настраиваемым User-Agent (некоторые провайдеры отдают разный формат в зависимости от него), таймаут 15 с. В режиме TUN запрос подписки идёт напрямую, а не через туннель.
- Форматы тела: base64 (стандартный и URL-safe, с паддингом и без) со списком ссылок, либо простой список ссылок. JSON-подписки - вне рамок, показывать понятную ошибку.
- Заголовок `subscription-userinfo` (`upload`, `download`, `total`, `expire`) разбирается и показывается в деталях подписки: использовано/всего, дата окончания. Заголовок `profile-title` - как имя подписки, если пользователь не задал своё.
- Обновление вручную (`u`) и автоматически по `auto_update_hours`. Ошибка обновления не удаляет старый список серверов.
- Сервер в подписке идентифицируется по паре (подписка, имя + адрес + порт), чтобы последний выбранный сервер сохранялся между обновлениями.
- Пинг:
  - режим `tcp`: время установления TCP-соединения до `host:port`, параллельно, не более 16 одновременно;
  - режим `url`: для каждого сервера временный экземпляр ядра с socks-инбаундом на случайном свободном порту и запрос `ping.url` через него; не более 4 одновременно; временные процессы в общем Job Object;
  - результат в списке: `NN ms`, `timeout`, `error`; сортировка по пингу клавишей `o`.
- Последний выбранный сервер и все настройки переживают перезапуск.

Критерии готовности:
- Реальная подписка импортируется, отображаются трафик и срок.
- Пинг всех серверов не подвешивает интерфейс.
- Отключение интернета во время обновления подписки - ошибка в UI, старый список на месте.

### Этап 7. Правила маршрутизации и пресеты

- Экран правил (`r`): список, добавление (`a`), удаление (`x`), включение/выключение (`Space`), типы `domain`, `ip`, `geosite`, `geoip`, `process`.
- Валидация ввода: домен, IP или CIDR (v4/v6), имя набора geosite/geoip, имя exe.
- Генерация правил routing в Xray (и в TUN-бэкенде, если это sing-box) с учётом режима `exclude` / `include`. Домены: `domain:` (с поддоменами), `full:` (точное совпадение), `keyword:`; пользователь выбирает вариант.
- В режиме PROXY простые домены и IP из правил «напрямую» дополнительно добавляются в `ProxyOverride` системного прокси.
- Изменение правил при активном подключении - перегенерация конфига и перезапуск (с подтверждением).

Встроенные пресеты в `presets.toml` (редактируемый файл, вшит через `include_str!`; пользовательские правила хранятся отдельно и не смешиваются с пресетами). Пресет включается одной клавишей и показывается в списке как группа, которую можно развернуть.

| Пресет | Суть | Содержимое (стартовое, уточнить при реализации) |
|---|---|---|
| `discord-only` | режим `include`: через VPN только Discord | процессы `Discord.exe`, `DiscordPTB.exe`, `DiscordCanary.exe` (Linux: `Discord`, `DiscordPTB`, `DiscordCanary`, `vesktop`); домены `discord.com`, `discord.gg`, `discordapp.com`, `discordapp.net`, `discord.media`, `discordcdn.com` (домены нужны, чтобы веб-версия и режим PROXY тоже работали) |
| `games-direct` | игры и лаунчеры напрямую | процессы `steam.exe`, `steamwebhelper.exe`, `EpicGamesLauncher.exe`, `RobloxPlayerBeta.exe`, `javaw.exe` (Linux: `steam`, `steamwebhelper`, `java`); домены `steampowered.com`, `steamcontent.com`, `steamserver.net`, `steamstatic.com`, `epicgames.com`, `roblox.com`, `rbxcdn.com` |
| `torrents-direct` | торрент-клиенты напрямую (через VPN-сервер их пускать нельзя - жалобы правообладателей хостеру) | процессы `qbittorrent.exe`, `utorrent.exe`, `BitTorrent.exe`, `transmission-qt.exe` (Linux: `qbittorrent`, `transmission-gtk`, `transmission-qt`, `deluge`) |
| `ru-direct` | российские сайты напрямую | `geosite:category-ru`, `geoip:ru` |
| `ua-direct` | украинские сайты напрямую | `geosite:category-ua`, `geoip:ua` |
| `local-direct` | локальная сеть напрямую (включён по умолчанию) | `geoip:private` |

- Пресеты с процессами в режиме PROXY применяют только доменную часть, в UI это видно.
- Если набора geosite/geoip из пресета нет в `.dat`-файлах - предупреждение, остальные правила пресета применяются.
- В режиме `include` пресеты «напрямую» не нужны и показываются неактивными.

Критерии готовности:
- Добавленный домен «напрямую» открывается с реальным IP пользователя (проверка через сайт, показывающий IP), остальные - с IP сервера.
- Пресет `discord-only` в режиме TUN: Discord через сервер, всё остальное со своего IP.
- Snapshot-тесты конфигов для каждого пресета в обоих режимах маршрутизации.

### Этап 8. Статистика и доводка

- Статистика трафика через встроенный API Xray: в конфиг добавляются `stats`, `api` (сервис `StatsService`), `policy.system.statsOutboundUplink/Downlink = true`, инбаунд `api` (dokodemo-door на `127.0.0.1:api_port`) и правило маршрутизации для него.
- Опрос раз в секунду через `xray api statsquery --server=127.0.0.1:<api_port>` (вызов того же бинарника, чтобы не тянуть gRPC-зависимости); в строке статуса - текущая скорость и суммарный трафик сессии отдельно для `proxy` и `direct`.
- Экран настроек: редактирование путей, портов, режимов, пинга, User-Agent, интервала обновления подписок, темы.
- Светлая и тёмная тема.
- Справка (`?`) генерируется из той же таблицы клавиш, что и обработчик, чтобы не расходиться.
- README: установка на Windows и Linux, где взять `xray`, `.dat`-файлы, `wintun.dll` и TUN-бэкенд, права для TUN на Linux, скриншот, клавиши, типовые сценарии («только Discord», «всё, кроме игр»).

Критерии готовности:
- Скорость в строке статуса совпадает по порядку величины с диспетчером задач при скачивании большого файла.
- Все настройки меняются из интерфейса без ручной правки `config.toml`.
